# 14 · 贡献系统：有界操作 + 升级给人

评审定调：**「改任何内容都可以沿用这种做法；如果改动太大，或者在我们现有体系下改不了，
那再让他主动 fork 并 PR。」** 并且：**机器人开的 PR 必须由维护者审核。**

---

## 1. 一条通用通道，两道闸

```
Issue 表单
   ↓
【第一道闸（a）】check job：立刻「干跑」——apply-issue.mjs --dry-run，**不写任何文件**，
            把「机器人打算改什么、改哪个文件、审核指纹」回帖出来
   ↓
【第一道闸（b）】维护者在**这个 Issue 里回复 `/approve`** → gate job 校验批准人权限，
            并取出「批准这条评论之前」那一版回帖里的指纹（= 他当时看到的那一版）
   ↓
【执行】apply job：指纹一致才写文件 → 跑 validate → **机器人自己开 PR（署名贡献者）**
   ↓
【第二道闸】PR 带 bot-pr + needs-review，自动请求 Code Owners 审核，
            main 的分支保护让它停在 `BLOCKED`，批准后才能合并
   ↓
   维护者审 PR → **点一次 Approve** → PR 上挂着的 auto-merge（squash）自动把它合掉
   （机器人在开 PR 时挂 auto-merge，但它自己**不决定**合并：没有人的批准，它就停在 BLOCKED）
```

**署名（归因要准）**：**提交作者 = 贡献者**（内容是人家定的），
**共同作者 = 机器人**（`github-actions[bot]`，它只是代笔把它写进文件）。
作者邮箱用 `<id>+<用户名>@users.noreply.github.com`（noreply 才是账号认得的身份，
先查 `users/<u>` 拿 id 与显示名）；committer 仍是机器人——这正是准确的归因：
谁提的、谁代的笔。署名取两个来源、去重：**提 Issue 的人**（GitHub 认过的身份）
与**表单里写的 GitHub 用户名**（目前只有「认领维护」那张表有）。

PR 作者仍是 `github-actions`——**这一点很重要**：如果 PR 作者是维护者自己，
他就不能批准自己的 PR，第二道闸就形同虚设。

**为什么是两道闸**：第一道审的是**意图**（这个请求该不该做），第二道审的是**结果**
（它具体改成了什么样）。只留一道的话，要么维护者被迫先信任一个还没发生的改动，
要么得在 PR 里替作者重做一遍判断。两道加起来，每条信息的判断成本都很低。

### 1.1 第一道闸为什么用「Issue 里 /approve」而不是 GitHub 的环境审批

两种做法都能挡住执行，实测下来选了前者：

| | Issue 里 `/approve`（当前） | 环境审批（原生） |
| --- | --- | --- |
| 批准的地方 | **Issue 同一串对话里**，贡献者看得见进度 | Actions / 部署审核页，**离开了上下文** |
| 批准理由 | 就是评论正文，天然可读（「日期可以改，但出处不够」） | 审批备注，藏得深 |
| 谁能批准 | 我写权限校验（查 `collaborators/<user>/permission` 必须是 admin/write） | GitHub 强制校验身份 |
| 批的是哪一版 | **评论式审批有洞**：批完还能改正文 → 用**审核指纹**补上 | 锁在那次运行的载荷上，天然防改 |
| 审计 | 评论本身就是审计 | 原生 Deployments 日志 |
| 额外对象 | 无 | 一个 environment |
| 绕过 | 无（但安全性取决于实现是否正确） | 默认 `can_admins_bypass: true`，可关 |

**结论**：贡献发生在 Issue 里，审批就该在同一串对话里——尤其这个项目只有一个维护者，
「把人从上下文里拽到另一个页面点按钮」的代价比原生实现带来的硬度更值钱。
换过来的**前提**是补上那个洞，也就是三道保险：

1. **权限**：只有对本仓库有写权限的人能批准（组织成员但只读也不行），机器人的评论不算；
2. **指纹**：批准时锁定「他看到的那一版」的哈希，执行时重算，不一致就拒绝并要求重新批准
   （`reason: stale-approval`）——这样「批完又改正文」改不出没被审过的内容；
3. **幂等**：同一个请求不会被执行两次（按 `bot/<op>-<issue>` 分支查已有 PR 就跳过）。

> 环境 `bot-apply`（required_reviewers）**仍留在仓库里**，作为备选第一道闸：想要
> 「不可绕过、审计在 Deployments 里、批准与运行载荷绑定」的形态时，把 `apply` job 加上
> `environment: bot-apply` 即可（那时应去掉 `/approve` 触发，否则会要批准两次）。

三类结果，三种回帖：

| 结果 | 回帖说什么 |
| --- | --- |
| 干跑通过 | 🕓 **已收到，等维护者批准后才动手** + 打算改什么 + **审核指纹** + 「回复 `/approve` 即可执行」 |
| **机器人不能安全地改** | 🙅 说明原因 + **请你自己 fork + PR** 的三步指引 |
| 表单没填全 / 值不存在 | 😕 说明哪里不对 + 「改一下本 Issue 就会自动重试」（不会进审批） |

### 1.2 两类 Issue：内容变更 vs 站点改进

站点所有 Issue 只分两类，路由靠**标题前缀**（机器人）与**标签**（人筛）：

| | **A 内容变更**（`内容变更`） | **B 站点改进**（`站点改进`） |
| --- | --- | --- |
| 说的是什么 | 某条词条 / 某个分区的内容 | **百科这个站点本身** |
| 例子 | 认领维护、改一个字段、改正文一句话、补充分区条目、纠错、新增词条 | 导航绕、搜索不好用、样式错乱、渲染坏了、表单流程别扭、想新增分区或词条类型 |
| 谁处理 | **机器人代改**（有界操作 → PR → 两道闸）；`纠错`/`新增词条`目前由人接手 | **人**——要判断、要设计，甚至要动信息架构与代码 |
| 表单 | `1-claim`、`2-field`、`3-replace`、`4-zone-item`（机器代改）+ `5-correction`、`6-new-entry`（人来接手） | `7-meta`（「站点改进 / 百科自身的问题」） |
| 入口 | 词条页标题栏、词条页右侧缺口清单、分区页「补充一条」 | **页脚**「反馈百科本身的问题」 |

**机器人只对 A 类的那两个前缀有反应**（`[内容变更]`、`[补充分区条目]`），B 类它**一声不吭**——
它插话只会变成噪音。表单覆盖的操作集合、workflow 认的前缀、`scripts/lib/ops.mjs` 声明的操作，
三者由 `scripts/check-workflows.mjs` 强制一致（漂移的表现是「机器人静默不工作」）。

#### 选择器：一行 = 一个意图（试过合并，更差，已回退）
**结论先说**：不要把多个操作合并成一张表单、再在表单里用下拉选操作。评审实测：
那样**越来越不直观**。原因很具体——**GitHub 不能预填表单字段**（只能预填标题），
所以从词条页点了「改一句话」的人，进来还要在下拉里**再选一次**，而且面对的是一张
「所有操作的字段并集」的长表。他明明已经表达过意图了。

（顺带的两个事实：选择器**原生不支持分组**——`config.yml` 只有 `blank_issues_enabled`
与 `contact_links`；顺序**按文件名 alphanumerically 排**，要定序就用数字前缀。）

所以现在是：**七张表，一行一个意图**，各自只问自己需要的字段（最多 5 项）：

| 顺序（文件名前缀定序） | 表单 | 字段 |
| --- | --- | --- |
| `1-claim` | 内容变更 · 认领维护 | 词条 id、用户名、关系（可选） |
| `2-field` | 内容变更 · 改一个字段 | 词条 id、用户名、字段名、新的值、出处 |
| `3-replace` | 内容变更 · 改正文里的一句话 | 词条 id、用户名、原文片段、改成、出处 |
| `4-zone-item` | 内容变更 · 补充分区条目 | 分区、二级分区 id、用户名、名称、一句话、外链 |
| `5-correction` | 纠错（只报告，不动文件） | 由人接手 |
| `6-new-entry` | 新增词条（申请） | 由人接手 |
| `7-meta` | 站点改进（反馈百科本身） | 由人接手 |

名字统一以「内容变更 · 」开头，四张机器代改的表在视觉上自成一组；顺序由文件名前缀定。

> **一个更正（也是这次回退的原因之一）**：GitHub **不支持**用 URL 预填 YAML 表单的字段
> （`issues/new?template=…` 只认 `title`、`body`、`labels`、`assignees`、`milestone`、`projects`、`type`）。
> 所以站点深链把**操作名与词条编号写进标题**（`[改一个字段] plugin/1`）——
> 机器人从标题尾部取编号，表单里的「词条 id」可以留空。这是**唯一**能预填的东西，用足它。
> 之前那些「点进来会自动填好」的说法是错的，已改。

> **还没用的两个办法**（都得上网页验真，我不凭猜上线）：
> ① 把几张表的 `name` 设成 ≤3 字符——官方文档说这样**不出现在选择器里**、但仍可被
> `?template=` 深链调用，能把选择器压到 4 条；风险是「深链是否仍能加载」本地验不了。
> ② 在站内做一个「我要贡献」面板充当第一级，GitHub 选择器只当兜底。

**为什么值得分成两类**：它们的**处理方式**完全不同。A 类可以交给机器（有界、可校验、可回归），
B 类不能——「导航怎么改」没有机械解，只有设计判断。把 B 类塞进「机器人代改」通道，
要么机器改错，要么它只能说「我改不了」，两头都不讨好。

### 1.3 署名契约：GitHub 用户名必填，且必须真实存在

署名是这套系统的**输出**，那它的输入就不能是可选。所以：

- **所有**机器代改的表单里，「GitHub 用户名」是**必填**字段（`1-claim`、`2-field`、`3-replace`、`4-zone-item`）；
- 校验分三道，任何一道不过就**直接拒绝**，绝不「凑一个署名」：
  1. **有没有**（缺 → `incomplete`）；
  2. **形状对不对**（GitHub 官方规则：字母数字与**单个**连字符、不能以连字符开头/结尾、≤39 位；
     顺手写的 `@name` 会被规范化去掉 @；不合法 → `bad-username`）；
  3. **账号真不真**——`apply-issue.mjs` 查 `GET /users/<name>`：404 → `unknown-user` **拒绝**；
     API 出错 → `user-lookup-failed` **也拒绝**（无法核实就不写下坏署名，改一下表单就会重试）。
- **提交作者 = 表单里这个用户名**（不再是「提 Issue 的人」）。两者不同时，提 Issue 的人
  作为共同作者一并列出——他确实提交了这次请求。机器人永远是 Co-author。
- 为什么这么较真：署名是我们**唯一**用来记「谁做的」的东西。写错一个字母，就会在提交里
  留下一个指向不存在账号的名字——那比不署名更糟，因为它看起来是对的。

守卫：`scripts/check-workflows.mjs` 会检查两张机器代改表单都把该字段设为 `required: true`；
`scripts/test-routing.mjs` 覆盖「缺用户名 / 形状不合法 / 带 @ 规范化」三条。

### 1.4 词条维护者：第一道闸可以放给他们，merge 仍在我们手里

评审定调：**「不是给他开权限，而是在第一道审核时让他们去通过；最后要 merge 还是需要我们过一下。」**

这正是最合适的分工——**两道闸分别放给不同的人**：

| | 第一道闸（这个请求该不该做） | 第二道闸（这份改动能不能进 main） |
| --- | --- | --- |
| 谁能批 | 仓库维护者（有写权限）**或本条词条的维护者** | 只有仓库维护者（分支保护要求 Code Owners 批准） |
| 需要给对方权限吗 | **不需要**——判断由我们的 workflow 自己做（`collaborators/<user>/permission` + `maintainers` 名单），不是 GitHub 的角色 | 不需要额外给；CODEOWNERS 指向仓库维护者 |
| 范围 | 词条维护者**只能批自己那条**（名单按被改的词条查） | 全仓库 |
| 实现 | `gate` job：`role=repo` 或 `role=entry` | 分支保护 + CODEOWNERS，机器人无 merge 步骤 |

具体表现：

- 干跑回帖里会 **@ 本条词条的维护者**：「你们也可以直接回复 `/approve` 批准（第二道合并仍由仓库维护者过）」；
- PR 描述里写明「第一道闸批准人：@x（**本条词条维护者**／仓库维护者）」，并把维护者列出来过目；
- 不是维护者也不是写权限用户时，回帖会**说清规则并列出本条维护者**（而不是一句「你没权限」）。

**这一步的信任含义要说清**：认领了某条词条的人，从此能批准**那条词条**的改动请求——
包括他自己提的。所以真正的兜底是第二道闸：内容进 main 之前，仓库维护者一定看过。
这也是为什么「给词条维护者 write 权限」不是一个好做法：那会让第二道闸对他也失效。

本地彩排：`bash dsh-pedia-preview/gate-test.sh`（7 项断言）——仓库维护者放行、
**无权限的词条维护者放行（role=entry）**、越权不放行、拒绝时说清规则、机器人评论不算、无人认领时外部人不能批。

## 2. 什么算「有界操作」

一个操作必须能回答三件事：**它改哪一处**、**什么情况下它拒绝**、**怎么校验它没改坏**。
声明在 `scripts/lib/ops.mjs`，一份派发器 `scripts/apply-issue.mjs` 处理所有操作——
所以新增一种贡献方式 = 加一条声明 + 一张表单，不用再写一个 workflow。

| 操作（Issue 标题前缀） | 改什么 | 明确的拒绝条件 |
| --- | --- | --- |
| `[认领维护]` | `maintainers` 加一个用户名 | 用户名非法、词条不存在、已经是维护者 |
| `[改一个字段]` | front-matter 里的**单值或列表**字段 | **嵌套结构**（`compat`/`relations`/`composition`）、字段名不像字段 |
| `[改正文里的一句话]` | 正文里**精确且唯一**的一处片段 | 找不到（可能在 front-matter 里）、**命中多处**（不猜是哪一处） |
| `[补充分区条目]` | 往某分区的某个二级分区追加一条卡片 | 分区不存在、二级分区 id 不存在、外链格式看不懂 |

**故意的窄**：宁可拒绝，也不猜。猜错的自动化比没有自动化更贵——它会污染内容，
而且作者以为已经改好了。

## 3. 什么时候升级给人（fork + PR）

`reason` 落在这一类就回帖教他 fork + PR：

- `unsupported` —— 改动落在机器人不碰的结构上（嵌套字段、块结构）；
- `ambiguous` —— 定位不唯一（片段出现多次）；
- `not-found` —— 找不到那段原文（可能已改过，或在 front-matter 里）。

**判据**：如果「机器人要改对」需要理解语义（改写一段话、调结构、判断哪个值对），
就不该自动化。那不是技术限制，是责任边界——猜错的责任没人负。

## 4. 审核：合并永远由人决定

- 每个机器人 PR 都带 `bot-pr` + `needs-review` 标签；
- `.github/CODEOWNERS` 让这些 PR 自动请求维护者审核；
- **人点一次 Approve 就够**（2026-10-02 起）：机器人开 PR 时会挂上 **auto-merge**（用
  `--merge`，**不是** `--squash`），批准一到它就把 PR 合掉，维护者不必再点一次「合并」。
  这里的关键是**决定权仍在人**：`main` 的分支保护要求 1 个 Code Owners 批准、
  且 `require_code_owner_reviews` 为真、CODEOWNERS 只写了仓库维护者，
  所以机器人**没有办法**让自己提的 PR 进入合并 —— 它只是执行已经批准的合并。
  workflow 里也**不得**出现 `gh pr review --approve` / `gh pr merge --admin`，
  这条约定由 `scripts/check-workflows.mjs` 第 ⑤ 项在 CI 里守着；
- **为什么不能用 squash**：署名契约要求「提交作者 = 贡献者、机器人只是共同作者」，
  而 squash 会**新建**一个提交、作者变成 PR 作者（机器人），把贡献者的署名吃掉。
  实测踩过：分支上的提交 `author=贡献者`（committer 是机器人、message 带
  `Co-authored-by: github-actions[bot]`），squash 到 main 之后变成
  `author=github-actions[bot]`，贡献者署名与 Co-authored-by 全没了。
  用 `--merge` 保留分支上的提交，署名原样落地；
- **分支清理**：合并后删 `bot/...` 分支，靠 `delete_branch_on_merge` **加**一层兜底
  （`.github/workflows/cleanup-bot-branch.yml`）—— 那个开关实测第一次没生效
  （`bot/claim-27` 在 #28 合并后仍在，可能是按 PR 创建时的设置判定的），
  兜底 workflow 只删 `bot/` 开头的头分支，别的分支不碰；
- **`main` 已开分支保护**（2026-10-02）：要求 1 个来自 Code Owners 的批准、新提交会撤销旧批准、
  禁止强推与删分支；但 `enforce_admins: false`——**管理员（你）仍可直推 main**，
  被挡住的是 `github-actions`（它不是管理员，绕不过）。

也就是说：「必须审核」现在是 GitHub **强制**的，不是约定；而你的操作习惯没变。

> **为什么没把 CI 设为必需检查**：`ci.yml` 带 `paths` 过滤（只对 `data/**`、`scripts/**`、
> `web/**` 触发）。若把它设成必需检查，一个只改 `docs/` 的 PR 会永远等一个不会跑的检查。
> 想让 CI 变成硬门禁，得先把 `paths` 过滤去掉（让它在所有 PR 上都跑）——**待定**。

这条不是形式：自动化有 write 权限，一旦它开始自己合并，「谁改的、为什么改」就断了。

## 5. 实测（不是「应该能行」）

| 场景 | 结果 |
| --- | --- |
| `[认领维护] plugin/1` | 分支 diff 只有 `maintainers: [] → [用户名]`（+1/−1），运行 success |
| `[补充分区条目] themes` | 往 `packs` 追加一条卡片，validate 0/0 |
| `[改一个字段] concept/1` | `updatedAt` 更新为表单给的值（**不带引号**，与文件既有风格一致——机器人的 diff 要干净到可以直接审） |
| `[改正文里的一句话]`（真实句子） | 正文里那一处被替换 |
| **两道闸**（`[改一个字段]` 全流程） | check job 干跑并回帖「等审核 + 指纹」→ `/approve` → apply job 改文件、跑校验、**自己开 PR**（PR #10）：作者 `github-actions`、标签 `bot-pr`/`needs-review`、自动请求 Code Owners 审核、状态 `BLOCKED` 等第二道闸 |

> **组织策略（已解决）**：组织原本禁止 Actions 创建 PR
> （`The organization does not allow GitHub Actions to create or approve pull requests`），
> 我们试过仓库级覆盖，被组织挡回。维护者随后在
> `Settings → Actions → General → Workflow permissions` 勾上
> 「Allow GitHub Actions to create and approve pull requests」——**现在机器人自己开 PR**，
> 实测 PR #10：作者 `github-actions`、标签 `bot-pr`/`needs-review`、自动请求 Code Owners 审核、

> `secrets.BOT_TOKEN || secrets.GITHUB_TOKEN`：万一将来策略又变，配一个账号令牌即可绕过，零代码改动。
>
> **改 workflow 后必须本地先过 YAML**：`node scripts/check-workflows.mjs`（CI 里也跑）。

> 而 GitHub **不报错**，只把那次推送记成 "workflow file issue"，真正的事件根本不触发。
> 这类失败**没有任何提示**，只能靠本地校验拦住。

## 机器代改的第五类：新增词条

| 项 | 决定 |
| --- | --- |
| **触发** | Issue 表单 `6-new-entry.yml`（标题 `[新增词条] …`），站点上的「写这一条」「申请收录这条」都进它 |
| **机器人做什么** | 领号 → 用表单里的**标题 / 一句话摘要 / 初稿正文 / 事实来源**建 `status: draft` 骨架 → 以**表单里的 GitHub 用户名**为提交作者 → 开 PR → 回帖告知编号 |
| **编号从哪来** | 当前 main 的 `registry.yml`：`nextNumber = max(counters[kind], 已分配最大号) + 1`（含墓碑，绝不撞已用号） |
| **幂等** | 同类型 + **同标题的草稿已存在就复用它的号**（`findDraftByTitle`）。所以重跑、重复提交都不会继续吃号 |
| **并发代价** | 两个 Issue 同时领到同一个号时，第二个 PR 会在 `registry.yml` 上**冲突**——可见、可恢复，维护者重跑一次即可；**不会静默改错** |
| **编号永久** | 因此一个最终没合并的草稿 PR 会**永久占掉一个号**（断号不回填是既有契约的必然结果） |
| **上线时机** | 骨架是 `draft`：**不合并就永远不上线**，两道闸照旧（`/approve` → PR review → 合并） |

彩排：`bash scripts/test-new-entry.sh`（15 项，含幂等与「表单不全就拒绝」，整棵工作树拷到临时目录跑，不碰真仓库的编号）。
