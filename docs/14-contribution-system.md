# 14 · 贡献系统：有界操作 + 升级给人

评审定调：**「改任何内容都可以沿用这种做法；如果改动太大，或者在我们现有体系下改不了，
那再让他主动 fork 并 PR。」** 并且：**机器人开的 PR 必须由维护者审核。**

---

## 1. 一条通用通道，两道闸

```
Issue 表单
   ↓
【第一道闸】check job：立刻「干跑」——apply-issue.mjs --dry-run，**不写任何文件**，
            把「机器人打算改什么、改哪个文件」回帖出来
   ↓
   维护者在这个 Issue 的 Actions 运行里点 Approve（环境保护规则：required_reviewers）
   ↓
【执行】apply job：needs check + environment: bot-apply → 才真的写文件 → 跑 validate → 开 PR
   ↓
【第二道闸】PR 带 bot-pr + needs-review，main 的分支保护要求 Code Owners 批准
   ↓
   维护者审 PR → 合并（机器人从不合并）
```

**为什么是两道闸**：第一道审的是**意图**（这个请求该不该做），第二道审的是**结果**
（它具体改成了什么样）。只有一道的话，要么维护者被迫先信任一个还没发生的改动，
要么得在 PR 里替作者重做一遍判断。两道加起来，每条信息的判断成本都很低。

**第一道闸怎么实现的**：workflow 里那个 job 声明 `environment: bot-apply`，而这个环境
配了必需审核者（维护者）。GitHub 会把这次运行**停在「等待批准」**，维护者在 Actions 页面
点 Approve/Reject，批准记录带审计。任务开始前就卡住——不是「跑完了等你删」。

三类结果，三种回帖：

| 结果 | 回帖说什么 |
| --- | --- |
| 干跑通过 | 🕓 **已收到，等维护者审核后才动手** + 机器人打算改什么（还没写文件） |
| **机器人不能安全地改** | 🙅 说明原因 + **请你自己 fork + PR** 的三步指引 |
| 表单没填全 / 值不存在 | 😕 说明哪里不对 + 「改一下本 Issue 就会自动重试」（不进审批队列） |

## 2. 什么算「有界操作」

一个操作必须能回答三件事：**它改哪一处**、**什么情况下它拒绝**、**怎么校验它没改坏**。
声明在 `scripts/lib/ops.mjs`，一份派发器 `scripts/apply-issue.mjs` 处理所有操作——
所以新增一种贡献方式 = 加一条声明 + 一张表单，不用再写一个 workflow。

| 操作（Issue 标题前缀） | 改什么 | 明确的拒绝条件 |
| --- | --- | --- |
| `[认领维护]` | `maintainers` 加一个用户名 | 用户名非法、词条不存在、已经是维护者 |
| `[改一个字段]` | front-matter 里的**单值或列表**字段 | **嵌套结构**（`compat`/`relations`/`composition`）、字段名不像字段 |
| `[改正文里的一句话]` | 正文里**精确且唯一**的一处片段 | 找不到（可能在 front-matter 里）、**命中多处**（不猜是哪一处） |
| `[补充分区条目]` | 往某分区的某个二级分区追加一条卡片 | 分区不存在、二级分区 id 不存在、外链格式看不懂 |

**故意的窄**：宁可拒绝，也不猜。猜错的自动化比没有自动化更贵——它会污染内容，
而且作者以为已经改好了。

## 3. 什么时候升级给人（fork + PR）

`reason` 落在这一类就回帖教他 fork + PR：

- `unsupported` —— 改动落在机器人不碰的结构上（嵌套字段、块结构）；
- `ambiguous` —— 定位不唯一（片段出现多次）；
- `not-found` —— 找不到那段原文（可能已改过，或在 front-matter 里）。

**判据**：如果「机器人要改对」需要理解语义（改写一段话、调结构、判断哪个值对），
就不该自动化。那不是技术限制，是责任边界——猜错的责任没人负。

## 4. 审核：机器人永远不合并

- 每个机器人 PR 都带 `bot-pr` + `needs-review` 标签；
- `.github/CODEOWNERS` 让这些 PR 自动请求维护者审核；
- workflow 里没有任何 merge 动作，**合并只能由人点**；
- **`main` 已开分支保护**（2026-10-02）：要求 1 个来自 Code Owners 的批准、新提交会撤销旧批准、
  禁止强推与删分支；但 `enforce_admins: false`——**管理员（你）仍可直推 main**，
  被挡住的是 `github-actions`（它不是管理员，绕不过）。

也就是说：「必须审核」现在是 GitHub **强制**的，不是约定；而你的操作习惯没变。

> **为什么没把 CI 设为必需检查**：`ci.yml` 带 `paths` 过滤（只对 `data/**`、`scripts/**`、
> `web/**` 触发）。若把它设成必需检查，一个只改 `docs/` 的 PR 会永远等一个不会跑的检查。
> 想让 CI 变成硬门禁，得先把 `paths` 过滤去掉（让它在所有 PR 上都跑）——**待定**。

这条不是形式：自动化有 write 权限，一旦它开始自己合并，「谁改的、为什么改」就断了。

## 5. 实测（不是「应该能行」）

| 场景 | 结果 |
| --- | --- |
| `[认领维护] plugin/1` | 分支 diff 只有 `maintainers: [] → [用户名]`（+1/−1），运行 success |
| `[补充分区条目] themes` | 往 `packs` 追加一条卡片，validate 0/0 |
| `[改一个字段] concept/1` | `updatedAt` 更新为表单给的值（**不带引号**，与文件既有风格一致——机器人的 diff 要干净到可以直接审） |
| `[改正文里的一句话]`（真实句子） | 正文里那一处被替换 |
| **两道闸**（`[改一个字段]` 全流程） | check job 干跑并回帖「等审核」→ apply job **waiting**（pending deployment，审核者=维护者）→ 批准后两个 job 都 success → 分支只差开 PR |
| 片段在正文里出现多次 | `ambiguous` + `escalate=true` → 回帖教 fork + PR |
| 改嵌套字段 `compat` | `unsupported` + `escalate=true` → 同上 |
| 二级分区 id 写错 | `unknown-section` + `escalate=false` → 提示改表单重试 |

> **一处组织策略限制**：本组织禁止 GitHub Actions 创建 PR
> （`Write permissions for workflows are disabled by the organization`），
> 所以 `gh pr create` 会被拒。workflow 因此**带回退**：分支与提交照做，
> 回帖里给出 `https://github.com/<repo>/pull/new/<branch>`，**只差人点一下**。
> 想完全自动：组织管理员在 `Settings → Actions → General → Workflow permissions`
> 打开「允许 GitHub Actions 创建并批准 PR」。
> 另一条路是存 PAT 当 secret；**本仓库没这么做**——长期凭据换一次点击，不划算。

## 6. 还没做的（同一套模式可以直接加）

| 操作 | 为什么还没做 |
| --- | --- |
| `[新增词条]`（自动领号 + 生成骨架 + 开 PR） | 要做并发保护：两人同时提交不能撞号。编号是永久的，这里不能出错 |
| `[撤下词条]`（墓碑） | 需要「为什么撤下」的语义，且影响面大（搜索、计数、反链），值得单独设计 |
| `[我来核实]`（更新 `updatedAt`） | 日期本身好改，但要确认「确实核实过」——需要一句声明，表单可以加，只是还没加 |
| `theme` 的截图画廊（展示契约里的 `gallery`） | 与贡献系统无关，等有真实素材 |
