## 1. MC百科是一台什么规模的机器（已核实）

| 指标 | 值 |
| --- | --- |
| 模组 | 2.07 万 |
| **物品（资料）** | **80.68 万** |
| 教程 | 5250 |

**这张表里最重要的一行是「物品 80.68 万」**：资料条目与模组的比例约 **39 : 1**。MC百科的体积与黏性主要不来自「两万个模组介绍」，而来自「每个模组下面那几十条物品/方块/合成表」。这是 DSH 百科最该学的结构，也是最难学的一条（见 §6）。

结构与入口（已核实）：

- 顶层：主站 / 社群（BBS）/ 找服玩 / 整合包 / 实用工具 / 特性（Bug 追踪）/ 入驻
- **核心元素 9 个**：科技、魔法、冒险、农业、装饰、实用、辅助、魔改、LIB。每个元素都有**一句官方定义**——这是分类树能被读者理解的原因（我们的 `taxonomy.yml` 里每个节点都有 `desc` 字段，正是同一个道理）
- 检索：独立域名 `search.mcmod.cn/s?key=`，结果**分栏**为 全部 / 模组 / 整合包 / 资料 / 教程 / 作者 / 用户 / 社群 / 服务器，并给出各栏计数；首页检索框另有「教程 / 版本 / 检索 / 拼音」四种模式
- 首页板块：最新收录 / 随便看看 / 有新动态 / 教程 / 社群动态 / 最受欢迎 / 版本检索 / 元素检索 / 热门标签 / 贡献榜（今日·本周·本月）/ 评比排行（趣味·稳定·美观·难度）/ 最新短评 / 视频教程 / 随机页面，以及**实时看板**：今日收录模组数、今日审核量、今日编辑量
- 编辑动态是**条目级**流水：「由 某某 编辑了资料 X 中的一张合成表（ID:221017）」——合成表本身有独立 ID、可被单独编辑
- URL 形态：`/class/<id>.html`（模组）、`/item/<id>.html`（资料）、`/modpack/<id>.html`（整合包）、`/post/<id>.html`（教程）、`/modlist.html`（条件检索）、`/class/history/` 与 `/class/diff/list/`（历史与差异）、`/rank/`（贡献榜）、`/verify/`（审核状态）、`center.mcmod.cn/<uid>`（用户中心）

## 2. 页面字段（已核实，逐页）

### 2.1 模组条目页

中/原名、简写名（渲染成 `[AE2]应用能源2`）、封面、**核心元素 + 多个子元素标签**（资源 / 世界 / 结构 / 生物 / 能源 / 存储 / 物流 / 道具 / 安全 / 红石 / 模型 / 破坏 / 建材 / 指令）、支持平台、运作方式（Forge / Fabric / NeoForge）、**运行环境（客户端需装 / 服务端需装）**、收录时间、编辑次数、最后编辑、最后推荐、模组标签、相关链接（官网 / CurseForge / Modrinth / GitHub / Discord / Crowdin / Wiki …）、支持 MC 版本（**按加载器分组**，`1.21.x(2)` 折叠）、作者与开发团队（带角色：所有者 / 开发团队 / 美术 / Mod 作者）、红黑票与八维属性评比百分比、开源/闭源徽标与许可协议声明、更新日志、历史编辑记录与对比、总浏览、资料填充率、指数。

下方挂载区：Mod 资料(N) / Mod 关系(N) / Mod 下载(N) / Mod 教程(N) / 合成表 / 日志 / 评论 / 讨论。

**明确不存在的字段**（已核实页面中不出现，不是「未核实」）：**收藏数**、**截图相册**、条目级保护等级。

> 逐块拆解（含 20 个区块的实测值与我们的对应物、采纳与不采纳的逐条判断）见 [09 · 条目页深挖](09-mcmod-entry-deepdive.md)——样本是 `机械动力（Create）`：1078 条资料、905 条关系、435 个整合包使用它、资料填充率 100%。

### 2.2 资料（物品 / 方块）页

物品命令（`/give`）、矿物词典（多标签多计数）、资料分类、最大堆叠、采集工具、最大耐久、图标（128/32 两档）、合并/综合（仅编辑员）、浏览量 / 创建日期 / 最后编辑 / 编辑次数、简介 / 生成 / 挖掘用时表 / 掉落物 / 用途 / 版本信息。

有意思的是：页面上**没有数据值 / 数字 ID 字段**（数字 ID 只出现在正文叙述里）——说明它的字段是围绕「玩家怎么用」组织的，不是围绕数据库主键。

### 2.3 合成表（最深的护城河）

- 渲染方式：**按 GUI 图片绝对定位格子**（像素坐标），支持工作台 3×3、锻造台、熔炉等；带「材料统计 / 输入 >> 输出 / 备注」汇总表
- 数据能力：有序（Shaped）/ 无序（Shapeless）、**开始版本 / 结束版本 / 模组要求 / 摆放要求 / 概率 / 数量 / 单位 / 燃料 / 能量条目**、多配方切换（最多显示 10 条）、申请删除而不是直接删
- 后台：有专门的 **GUI 管理**，为每个 GUI 上传底图并拖拽对齐格子

### 2.4 模组关系（第二条护城河）

**前置 / 拓展（附属）/ 联动** 三类，按版本段分组，并提供「打开星图」——**模组关系可视化**。

### 2.5 教程页与整合包页

- 教程页：面包屑回到所属模组、教程权限（社区教程 / 官方教程）、浏览量、创建日期、正文、历史编辑记录与对比、最近浏览
- 整合包页：差异字段为整合包类型（如「魔改整合」）、运作方式、打包方式、整合包标签、制作团队（带角色）；正文含「游戏的任务发展流程」分级
- **整合包页的「包含模组 (191)」是按分组列出的每个模组名 + 精确版本号**（如 `AE2 Stuff 0.8.5-GTNH`），另有整合包教程 (42) 与画廊——这正是我们「整合包配方」视图要抄的东西，而我们比它更有优势：DSH 的版本是**坐标钉死 + 可校验哈希**的，能做得更精确

### 2.6 编辑与收录机制

- 用户组 6 个：百科用户 / 百科编辑员 / 资深编辑员 / 禁止编辑 / 禁止发言 / 禁止访问；权限矩阵含「免审核编辑」「进入后台」「后台审核」「删除条目」；编辑员需要 QQ 群或论坛申请
- 后台：模组管理、日志管理、**GUI 管理**、模组元素管理、MC 版本管理、资料管理（列表 / 合并 / 综合 / 分类管理）、文件管理、举报管理、安全管理
- 编辑器支持富文本（推荐）与 Markdown；历史编辑有记录与 diff 列表
- 举报入口在短评右下角，需填理由，未登录不可举报

## 3. 逐项对照

| MC百科 | DSH 百科 | 差异说明 |
| --- | --- | --- |
| 模组（`/class/`） | **插件**（`plugin/<owner>.<repo>`） | 生态既有 `owner.repo` 标识可直用 |
| 物品 / 方块（`/item/`） | **资料**（首版不单独成页；先写进插件词条与教程，列为 M3 可选机制） | 对应「工具 / 命令 / 技能 / UI 组件 / 配置项」 |
| 合成表（GUI 图 + 像素格子 + 材料统计） | **整合包配方** | 不是二维格子而是分层挂载（[01](01-information-architecture.md) §5）；但「材料统计」思路要抄 |
| 模组关系（前置/拓展/联动 + 星图） | **关系**（`requires` / `integrates` …）+ 关系图 | 起点是 manifest 的 `dependencies` + 人工补充 |
| 9 个核心元素（各带一句定义）+ 自由标签 | **taxonomy 分类树（每节点带 `desc`）+ tags** | 双轨制照抄 |
| 「加载器 × MC 版本」折叠的版本矩阵 | **「DSH 版本 × profile × 平台」矩阵** | 对 DSH 更关键（`rc` 版本 + 插件易失效） |
| 整合包页的「包含模组 (191) + 精确版本」 | **合成表**里的坐标 + 钉死版本 | 我们还能显示 `sha256` 校验信息 |
| 更新日志 + 历史编辑 + diff | **版本变更 + git 历史与 diff** | git 天然具备，成本更低 |
| 用户组与审核后台 | **PR + CI 校验 + maintainer 名单** | 不抄后台（见 §5） |
| 独立搜索域 + 9 个分栏 | 单页搜索 + 分栏（词条 / 资料 / 教程） | 首版不做「作者 / 用户 / 社群 / 服务器」栏 |
| 启动器（无对应概念） | **启动器词条** | DSH 生态特有：安装端有 canonical ID 注册表 |

## 4. 值得照搬的机制（按价值排序）

1. **资料层（39 : 1 的深度）**——**列为首选但排在 M3**。这是百科与「一行一个链接的清单」的分水岭，DSH 落点是插件的工具、斜杠命令、slot UI 组件、配置项逐条成资料。之所以不放在首版：见 §6 的结构性差异（MC百科能批量导出，我们没有现成通道）。首版先用「插件词条里的能力分块 + 教程用例」承载同样的信息。
2. **合成表可视化与它的「材料统计」**。`bundles` + `dependencies` + 技能 + 预设 + 指令 + patch 摘要，逐项列出并标明来源与钉死版本。MC百科的「材料统计 / 输入 >> 输出」汇总表尤其值得抄。
3. **关系三类（前置 / 拓展 / 联动）+ 星图可视化**。我们的 `relations.yml` 直接采用同构的类型划分，并做一张可点开的生态星图。
4. **分类元素 + 每个元素一句官方定义**。MC百科的 9 个元素各有定义，读者才能理解分类。我们的 `taxonomy.yml` 已要求每节点 `desc`——这条是它的存在理由。
5. **版本矩阵按维度折叠**（它按「加载器 × MC 版本」）。我们按「DSH 版本 × profile（web/headless）× 平台」，并标注「实测」与「未核实」的区别。
6. **条目级编辑流水 + 首页实时看板**（今日收录 / 审核量 / 编辑量）。把死站变活站最便宜的手段；我们的等价物是 `#/recent` + 构建期统计。
7. **更新日志 + 历史编辑 + diff 对比**。git 直接给。
8. **随机页面（「手气不错」）**。实现成本一行代码，探索性收益高。

## 5. 不该照搬的机制

| 机制 | 为什么不抄 |
| --- | --- |
| 积分 / 等级 / 成就 / 贡献榜百分比 | 需要账号体系、活跃度统计与防刷；DSH 百科早期没有这个后端与运营人手，一上线就会变成刷量战场 |
| 举报 / 审核 / 封禁后台与 6 级用户组 | 属于运营成本而非产品功能；我们的等价物是 PR 评审 + `validate.mjs` 机器校验 + maintainer 名单 |
| 短评分频道（不同频道不同发言门槛） | 历史包袱式设计；要讨论就用 GitHub Issues / Discussions，同一批人、同一套身份 |
| **BY-NC-SA 3.0 + 封闭编辑队伍** | 与 DSH 生态「数据可被下游机器消费」的方向冲突。我们要的是**开放格式 + 宽松许可**，才能喂给市场、启动器这类下游（见 [03](03-directory-and-pipeline.md) §7） |
| 自建文件托管与下载授权体系 | 分发已由 GitHub Release / npm / `.dspack` 侧车承担；百科只做元数据与索引，不做第二个下载站 |
| 评分（红黑票、八维评比） | 没有账号就无法防刷；且百科的定位是「记录生态」而不是「推荐清单」，打分会损害中立性 |
| 矿物词典 / 矿物分布 / 找服玩 | 无对应物，不要为了「像」而硬造 |

## 6. 一处结构性差异：我们的「资料」比 MC百科难写

MC百科的资料量级能到 39 倍，靠的是**从 Mod 的代码与资源批量导出**（社区有专门的「批量添加资料 JSON 收纳帖」这类机制，回复数已达数千），再加一个可拖拽对齐的 **GUI 管理**后台。DSH 插件**没有现成的导出通道**：工具清单要读 `cordis.patch.yml` 与插件源码，slot 名要扫客户端 bundle。

所以首版要把预期放低：

- MC百科：资料 ≈ 模组 × 39
- DSH 百科首版目标：**资料 50+ 条，集中在 2 个「工具密集」插件上**（[05](05-content-plan.md) §9）

真正的效率机会在于：**从 `cordis.patch.yml`、`package.json` 的 `dsh.client.inject`、preset 的 `agent.cordis.yml` 行结构里半自动提取「资料候选」**。这是 DSH 生态比 MC百科当年占便宜的地方，值得作为 M3 之后的专门课题。

## 7. 与既有同类站点的边界

### 7.1 awesome-dsh-plugin.com（已核实）

| 项 | 事实 |
| --- | --- |
| 定位 | **纯目录站**：首页除条目页外只有 feed / logo / 字体 / `catalog.json` / privacy；全文没有「教程 / 指南 / 概念 / FAQ」类内容（「什么是 DeepSeek Harness？」直接外链官方仓库） |
| 规模 | 收录 **4400 条**（JSON-LD 的 `numberOfItems`、页面计数、`catalog.json` 的 `items.length` 三者一致），24 个分类，中英双语 |
| 条目字段 | `cat`（分类）/ `tag`（中文分类名）/ `dl`（近 30 天下载量）/ `stars` / `added`（收录日期）/ `npm`（是否可从 npm 安装）/ `name` / `owner` / `short` / `slug` / `desc` / `cmd`（安装命令）/ `href` |
| 详情页 | **有**：`/zh/p/<owner>/<plugin>/`；sitemap 共 8850 个 URL，其中约 8800 个是详情页（中英双份）。详情页字段 = 面包屑、Star、下载量（近 30 天）、分类、收录日期、npm 包名、一句话描述、安装命令（npm 与 GitHub 两种）、安全免责声明、**README 正文（直接从仓库抓取，不做二次撰写）** |
| 交互 | 搜索、分类 chip、排序（下载量 / Star / 最新收录 / 名称）、开关（可从 npm 安装 / 近 7 天新增）、安装命令一键复制 |
| 投稿 | 给仓库提 PR，在 `data/plugins/` 下新增一个 YAML 即完成投稿，并给仓库打 `dsh-plugin` topic |

**边界**：awesome = 发现 / 收录 / 元数据 / 安装命令；DSH 百科 = 解释 / 术语 / 教程 / 关系 / 版本兼容 / 整合包内容构成。两者**只做外链互指**，不互相复制数据。

| 维度 | awesome-dsh-plugin.com | DSH 百科 |
| --- | --- | --- |
| 一句话定位 | **发现**：有哪些插件、怎么装 | **解释 + 整合**：这是什么、和谁一起用、哪个版本能用、包里装了什么 |
| 内容单元 | 插件（4400 条，扁平，正文 = 上游 README） | **六类词条**：概念 / 插件（聚合页）/ 教程 / 整合包 / 启动器 / 资源源 |
| 插件覆盖面 | **全量** | **按门槛**：官方来源 / 被教程引用 / 被整合包使用 / 有人认领；不做全量收录 |
| 热度数据 | 自建（每日快照 star / 下载量） | **引用它的数据**（建条时抓一次 + 标快照日期 + 外链） |
| 版本信息 | 无 | **核心**：DSH 版本 × runtime × 平台 的兼容矩阵 |
| 关系 | 无 | **核心**：前置 / 联动 / 冲突 / 替代 |
| 整合包 | 无 | **核心**：包成分表（含精确版本锁定） |
| 教程 | 无 | 有，但避开入门向（dshbase 已占），并给外部教程做索引卡 |

**四条边界纪律**

1. **数据不互抄，只互链**：百科不维护自己的 star / 下载量，建条时引用一次并标快照；awesome 也不需要抓我们的字段说明。
2. **插件词条必须是「聚合页」而不是「README 页」**：外部源指针 + 人工写的定位/关系/兼容/坑 + 挂教程 + 出现在哪些包。若一页读下来与 awesome 详情页无异，这页就不该存在。
3. **百科必须持有 awesome 没有的三样东西**：关系、兼容矩阵、包内容构成——这是「值得建百科」的全部理由。
4. **百科的插件索引页只列本站已收录的词条**，并显式外链「生态全量请去 awesome / dshbase」。若它长得像 awesome 的 4400 条列表，定位就错了。

一个重要细节：awesome 的 24 个分类是现成的体系，**百科不要另造一套平行的分类键**——应当复用它的 `cat` 键（只在需要更细粒度时加第二层标签），否则同一个插件在两站会落在不同的类里，读者与下游机器都要做映射。

### 7.2 dshbase.com（已核实）

`dshbase.com` 的自我描述是「DeepSeek Harness 中文指南、教程与插件生态」，站内包含**中文指南/教程、插件目录、场景包、皮肤、贡献者、审计、排错、博客**。

这件事实直接改变了我们的边界划分：

| 位置 | 已被占住 | 对 DSH 百科的含义 |
| --- | --- | --- |
| 「有哪些插件、怎么装」 | awesome-dsh-plugin.com（4400 条 + 详情页 + 安装命令） | 我们**不做第四份插件目录** |
| 「DSH 是什么、怎么入门、怎么排错」 | dshbase.com（中文指南与教程） | 教程要**避开入门向**，聚焦「这个插件怎么用 / 怎么配」，以及**别处查不到的**：关系、版本兼容、包内容构成 |
| 「有哪些包、怎么装上」 | dsh-pack-market | 我们读它的索引，不重复采集 |

结论：DSH 百科的差异化空间在 **解释 + 关系 + 版本兼容 + 包内容构成**，而不是「又一份列表」或「又一套入门教程」。若首页长得像 awesome 的列表，这个项目就已经失败了——首页应该是分类树 + 概念入口 + 最近变更。

### 7.3 一处必须处理的事实风险：许可证口径不一致

- `dsh-pack-market/web/index.html` 的页脚写着：「特别感谢 awesome-dsh-plugin.com（**CC0 1.0**）——设计灵感与视觉风格源自于此。」
- 但该站自己 README 的 License 徽标与正文写的是 **MIT**（经第三方镜像核实的 README 原文；直连 `raw.githubusercontent.com` 时连接被重置，未能二次直连确认）。

所以**市场页脚的那句署名很可能是错的**。对百科的影响与处理：

1. 百科的视觉系统**已改为自定的一套**（现代 Wiki / 索引式，见 [08](08-visual-system.md)），不再复用市场的「纸墨朱砂」，因此**不产生该署名义务**；页脚只做自愿鸣谢 + 外链，**不写任何具体协议名**。
2. 市场页脚的口径问题仍应**回报给 `dsh-pack-market`** 修正（改成「设计灵感源自 …」+ 链接，或先补一次上游许可核对）。
3. 这条也说明一个通用纪律：**引用别人的东西时只写「引用自哪里」，不替对方声明许可**。

---

## 8. 结论：DSH 百科的差异化公式

```
DSH 百科 = MC百科的词条化骨架（词条 / 资料 / 配方 / 分类 / 关系星图 / 版本矩阵 / 编辑历史）
         − 社区运营负担（账号 / 积分 / 评分 / 评论频道 / 审核后台 / 自建下载）
         + 生态既有的结构化数据（市场索引 / manifest / SKILL.md front-matter / 启动器注册表 / git 历史）
```

第三项是我们比 MC百科起步时**占便宜**的地方：MC百科当年要在没有结构化数据的 Minecraft 生态里从零积累，而 DSH 生态已经有索引契约、manifest v5、启动器注册表和一份可复用的 `.dspack` 解析器。所以工作量的大头应该放在**人工独占的那部分**（概念解释、关系、资料、教程），而不是重复造采集。
