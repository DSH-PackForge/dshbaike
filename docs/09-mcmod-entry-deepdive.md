## 2. 这一页教给我的三件事（结构性）

1. **条目页是「工作台」，不只是「说明书」**。按钮组把「编辑、新建日志、新建资料、新建教程、上传、讨论」全放在条目页上——读者在阅读位置就能贡献，且**新建的下级内容自动挂到当前条目**。这解释了为什么它的资料能长到 1078 条：**贡献入口就在读的地方**。
2. **「完整度」是一种内容驱动力**。`资料填充率 100.00%` 让「这条词条写全了没有」变成公开数字。它比任何「请补充内容」的号召都有效——因为它可比较、可进步、会被人盯着看。
3. **关系必须带时间维度**。905 条关系不是一张大图，而是**按版本段分组**：`Create 0.5.0g 之前需要 Flywheel`、`1.16.x 有 28 个附属`、`1.18.x 有 70+ 个附属`。没有版本段，关系表会在生态演进后变成误导。

## 3. 直接采纳的四条（含契约改法）

### 3.1 完整度（`completeness`）

构建期派生，**不进 front-matter**：`completeness = 已填必填/推荐字段数 ÷ 应有字段数`，按 kind 定义分母（插件：定位/正文/关系/兼容/外部源指针/出现在哪些包；教程：难度/前置/适用版本/正文/引用插件）。页面在信息表下方显示一条细进度条 + 百分比，**并列出「还缺什么」**（缺 `compat` → 「兼容性未声明，点这里补」）。

与「资料填充率」的差异：它是**我们自己的字段完备度**，不是转载率；且**缺项可点击直达贡献入口**，比一个纯数字更有用。

### 3.2 作者角色（`roles`）

```yaml
roles:
  - { who: Simibubi, role: owner }
  - { who: dsh-plugins, role: maintainer }
  - { who: Shigma, role: upstream, note: Cordis 上游作者（vendored） }
```

允许的角色：`owner` / `maintainer` / `contributor` / `translator` / `upstream`。`upstream` 尤其重要——DSH 大量依赖上游（Cordis 是 vendored 的第三方框架），把上游作者写清楚是诚实，也避免读者误以为是 DeepSeek 原创。

### 3.3 关系带版本段（`since` / `until`）

```yaml
relations:
  - { type: requires, target: plugin/14, since: "0.1.0-rc.1", until: "0.1.0-rc.6", note: 之后内置了 }
  - { type: integrates, target: plugin/18 }
```

页面按 `until` 分组渲染，组标题形如「**≤ 0.1.0-rc.6**」「**0.2.x**」「**未标注版本**（默认视为现行）」。规则：**`since`/`until` 缺失即视为现行**；已 `until` 的关系标灰并提示「历史关系，现行已不适用」——**不删除**（照 MC百科「不要因为有版本说明就删」的纪律）。

### 3.4 条目页上的「派生下级内容」入口

词条页按钮组（我们版）：

| 按钮 | 行为 |
| --- | --- |
| 编辑此条 | 深链到 GitHub 编辑该文件 |
| 纠错 | Issue 模板，预填词条 id 与当前字段值 |
| **为它写一篇教程** | 领号后生成 `tutorial/<n>.md` 骨架，**自动写入 `plugins: [{ entry: plugin/12, why: "" }]`** 与 `prereq` |
| **从这里派生概念/资料** | 同上，自动带父级引用 |
| 复制安装命令 | 复制 `dsh plugin …` |

这是「贡献入口在读的地方」的落地，也是我们红链机制的正向补充（红链是「缺条目」，这里是「已有条目的下级内容」）。

## 4. 改造后采纳的三条

| MC百科机制 | 我们的改造 | 理由 |
| --- | --- | --- |
| 资料填充率 100% | **完整度** = 我们自己的字段完备度，且缺项可点击 | 它是「转载率」；我们要的是「词条写全了没有」 |
| 元素标签 13 个 | 复用 awesome 的 24 类 + DSH 专属补充（`兼容层/注入器`、`桌面操控`、`凭据代理`、`构建脚本`） | 不造第三套体系，但 DSH 的真实风险类别必须能筛 |
| 指数 + 等级称号（5.0 名扬天下） | **两个可解释的客观量**：被本站教程引用次数 + 被整合包使用次数（构建期可算，不可刷） | 它的指数公式不公开、等级称号带运营色彩；我们要的是读者能自己验证的热度 |

## 5. 明确不抄的五条

| 不抄 | 原因 |
| --- | --- |
| 8 维属性评比（好玩/很漂亮/兼容好…） | 需要账号 + 长期样本 + 反刷；且 DSH 插件维度不同（该评「稳定」「兼容」「侵入性」而不是「漂亮」） |
| 红黑票 | 同上；且二元投票对工具类资源信息量低 |
| 昨日指数 / 总浏览 / 等级称号 | 需要服务端埋点与不公开的公式；我们用反向索引的客观量替代 |
| 最近浏览名单（公开 18 个用户名） | 隐私问题；且我们没有账号体系 |
| 上传 JSON（批量灌资料） | 它是从 Mod 代码批量导出的通道；DSH 没有对应通道（[04](04-mcmod-reference.md) §6），资料留 M3 且必须人工 |

## 6. 对现有设计的三处修正

1. **[01](01-information-architecture.md) §4 词条页骨架**：补三块——**完整度条（含缺项入口）**、**许可证独立分块**（对应 `Mod协议 (2)`）、**关系按版本段分组**；按钮组补「为它写一篇教程 / 派生下级内容」。
2. **[02](02-data-contract.md) §3.2**：插件与整合包词条新增 `roles`、`relations[].since` / `relations[].until`、`licenseRefs`（可多条协议，如「本体 MIT + 内置资源 CC BY」）；`status` 枚举增加 `archived`（上游已归档，页面挂「已归档」徽标）；构建产物新增 `completeness`。
3. **[06](06-zones-and-entries.md) §4 卡片字段**：卡片右下角增加**完整度小标**（仅对已有词条的条目显示），让分区页也能看出「哪条还没写全」——把编辑驱动力放回分区层。

> 另一处顺带印证：[02](02-data-contract.md) §4 要求 taxonomy **每个节点写一句定义**是对的——MC百科把分类定义做成了面包屑上的 tooltip（`科技Mod` 的 title 就是那句「设定可在现实中找到相关原始理论…」）。
