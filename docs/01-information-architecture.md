## 1. 站点定位与内容边界

| | DSH 整合包市场（既有） | **DSH 百科（本项目）** | 外部源（awesome / dshbase，既有） |
| --- | --- | --- | --- |
| 回答的问题 | 「有什么包，怎么装上」 | 「这是什么，为什么，和谁冲突，包里装了什么」 | 「有哪些插件 / 怎么入门」 |
| 内容形态 | 列表 + 安装命令 + 包元数据 | **六类词条**：概念、插件（聚合页）、教程、整合包、启动器、资源源 | 扁平目录 + README 详情页 / 中文指南 |
| 数据源 | 采集 GitHub topic `dsh-pack` | 人工词条为主 + **引用**外部源（带快照） | 自动快照上游仓库 |
| 覆盖策略 | 全量（topic 命中即收） | **按门槛**（被用到或有人认领），不做全量 | 全量（4400 条 / 7800+ 条） |
| 深度 | 一屏 | 一个实体一页，可交叉链接 | 一行 / 一篇 |

一句话：**市场负责分发，外部源负责发现与入门，百科负责解释与整合**。各方互相深链，不互相复制正文。

**百科自身也是两个功能**（详见 [06](06-zones-and-entries.md)）：

| 功能 | 形态 | 是否编号 | 数据来源 |
| --- | --- | --- | --- |
| **分区层**（资源整合） | **十一个**一级分区页 + 卡片列表，**大量外链，顶多一句介绍** | **不编号**（不是词条） | `external-index`（awesome / 市场 / launchers）或 `curated-list`（人工 YAML） |
| **词条层**（解释与教程） | 编号词条页 `/<kind>/<n>.html`，用户贡献 | 编号，永不复用 | 人工撰写 + 引用外部源（带快照） |

两层之间靠**红链**连接：分区页里还没有词条的条目显示「写这一条」，点进去就是领号命令与模板。

## 2. 站点地图与路由

词条页用**真实路径 + MC百科式数字编号**，其余用 hash 路由：

| 路由 | 页面 | 说明 |
| --- | --- | --- |
| `/` | 首页 | 搜索 + **分区导航** + 资源源目录 + 教程与最近更新 |
| `/clients` `/plugins` `/packs` `/launchers` `/themes` `/skills` `/presets` `/recipes` `/toolchain` `/specs` `/assets` | **分区页（资源整合层，共 11 个）** | 卡片 + 外链 + 红链；**不编号、不写正文**，最多一句介绍（见 [06](06-zones-and-entries.md)） |
| `/concept/<n>.html` | 概念词条 | 词条页（静态生成） |
| `/plugin/<n>.html` | **插件词条（聚合页）** | 与 MC百科 `/class/<n>.html` 同一形态：信息表 + 外部源指针 + 关系 + 兼容 + 挂教程 |
| `/tutorial/<n>.html` | 教程词条 | 自写与外部索引卡共用同一 schema |
| `/pack/<n>.html` | 整合包词条 | 含**包成分表** |
| `/launcher/<n>.html` | 启动器词条 | |
| `/source/<n>.html` | **资源源词条** | 外部插件源/渠道一页：它收录什么、提供哪些字段、怎么用、怎么投稿 |
| `#/sources` | 资源源目录 | 按类型列出全部外部源 |
| `#/plugins` | 插件索引 | 本站**已收录**的插件词条筛选（不是生态全量；生态全量交外部源） |
| `#/browse/<kind>` | 按类型浏览 | `concept` / `plugin` / `tutorial` / `pack` / `launcher` / `source` |
| `#/category/<taxonomy-id>` | 按分类浏览 | 分类树的叶子节点 |
| `#/search?q=…` | 搜索结果 | 分栏：词条 / 分区条目 / 教程 |
| `#/graph` | 关系图 | 前置 / 联动 / 冲突（插件词条之间的关系） |
| `#/matrix` | 版本兼容矩阵 | DSH 版本 × 插件（数据来自插件词条的 `compat`） |
| `#/recent` | 最近更新 | 按 `updatedAt` 与 registry 的创建时间 |
| `#/contributing` | 贡献指南 | 含**领号**流程（`node scripts/new.mjs`） |

三条规则：

1. **词条页不用 hash 路由**：hash 链接拿不到服务端渲染的标题与摘要，搜索引擎也无法区分词条。构建期为每条词条吐一个 `index.html` 外壳（复用同一套 JS/CSS，编号内联），文件数 = 词条数。
2. **编号即身份**：数字由 `data/registry.yml` 固化，**永不复用**；删除留墓碑页（`status: deleted`），所以链接不会烂（契约见 [02](02-data-contract.md) §2）。
3. **插件词条与插件索引是两件事**：索引页只列**本站已收录**的插件词条（十几到几十条量级），并明确给出「生态全量请去 awesome-dsh-plugin.com / dshbase.com」的外链。索引页长得像 awesome 的 4400 条列表，就说明定位错了。

- **资源源区块放在首屏**：第一屏就承认「插件全量收录不在我们这里」，并指出该去哪。这是定位的可见化，也是与 awesome / dshbase 的互链入口。

### 4.1 按词条类型变化的区块

| kind | 正文之外挂什么 |
| --- | --- |
| `plugin`（聚合页，MC百科 `/class/<n>.html` 的对应物） | **元素标签行**（二级标签，链到筛选）、**外部源指针区**（awesome 详情页 / npm / GitHub / dshbase：star、下载量、收录日期、许可——全部引用并标快照时间）、**关系**（前置 / 联动 / 冲突 / 替代，**按版本段分组**，链到对方词条）、**兼容**（DSH 版本枚举 × runtime × 平台，分组 + 折叠 + 计数，标「实测 / 未核实」）、**它提供了什么**（工具 / 命令 / slot / 配置项，按类型分组带计数）、**出现在哪些整合包**（反查 `bundles`/`dependencies`，显眼位置 + 一键跳分区筛选）、**哪些教程用了它**（反向索引）、**许可证**独立分块（可多条：本体 MIT + 内置资源 CC BY）、安装命令、**装它会发生什么**（§5.1）、**完整度条**（§4.4） |
| `pack` | **包成分表**（§5）、profile 列表（dshhome 形态）、内含技能与预设（profile 形态需解包）、启动器声明、安装命令、校验信息（`sha256` / 大小 / 下载地址）、下载量（引用市场 `stats.json`，取不到写「无数据」）、`fitFor`（人工写的「适合谁」） |
| `launcher` | canonical ID、支持的 manifest / 包结构版本、平台、与整合包词条的互为两面（包声明支持哪些启动器） |
| `concept` | 所属层级、**权威出处**（代码路径或规范文档 URL）、相关概念、被哪些词条引用 |
| `tutorial` | 难度、前置词条、适用版本（带实测口径）、正文步骤、**引用的插件块**（§4.2）、相关词条；`origin: external` 时额外显示原站、作者、我们的适用性判断与复查日期 |
| `source`（资源源） | 它收录什么、提供哪些字段、收录量与快照日期、许可、与我们互补还是重叠、怎么用 / 怎么投稿、默认把读者送去哪个 URL |

> 技能、预设、资料（`resource`）在首版**不单独成页**：技能与预设写进整合包词条与教程，资料列为 M3 可选机制（见 [02](02-data-contract.md) §1.1）。

### 4.2 插件引用块在页面上的样子

教程与整合包页里引用插件时，不写成裸链接，而是渲染成一张紧凑的引用卡——这是「资源整合」的可见形态：

```
┌─ dsh-loader ───────────────────────────────────────────────┐
│ 版本感知的运行时兼容层，让第三方插件在 dsh 升级后无需改动。 │
│ npm @dsh-plugin/dsh-loader · github: dsh-plugins/dsh-loader │
│ 兼容 dsh 0.1.0-rc.6（实测） · CLI / 桌面端 / Web            │
│ [复制安装命令]  词条 → /plugin/12.html                       │
│ 外部源：awesome-dsh-plugin.com ↗ · npm ↗ · GitHub ↗         │
│ 在这篇教程里的作用：不修插件源码就扛过升级                  │
└────────────────────────────────────────────────────────────┘
```

有词条时优先链词条页（`entry: plugin/12`），没有词条时才直接指向外部源——这样「教程引用」会成为插件词条最自然的生长来源。

### 4.3 三个界面细节

1. **信息来源可见**：每个采集字段后面挂「自动采集 · 快照时间」或「人工核实 · 日期」（契约见 [02](02-data-contract.md) §7）。读者据此判断可信度。
2. **红链（wiki 生长机制）**：链接到未收录的词条时显示为灰色虚线下划线，点击进「申请收录」页（GitHub Issue 模板预填词条 id）。这是 MC百科式的生长方式——先有人写、后有人补。
3. **编辑入口深链到 GitHub**：`[编辑此条]` 指向 `https://github.com/DSH-PackForge/dshbaike/edit/main/data/<kind>/<n>.md`。没有用户系统与在线编辑器，改词条 = 提 PR（新建词条先领号，见 [03](03-directory-and-pipeline.md) §2）。

### 4.4 完整度条与「派生下级内容」入口

这两条都来自对 [机械动力条目页](09-mcmod-entry-deepdive.md) 的拆解——它的 `资料填充率 100.00%` 与「新建资料 / 新建教程」按钮组，是那页能长到 1078 条资料的原因。

**① 完整度（`completeness`，构建期派生）**

信息表下方一条细进度条 + 百分比 + **缺项清单**：

```
完整度 78%  ████████████░░░░  ⚠ 兼容性未声明（点这里补） · 未关联任何教程
```

分母按 kind 定义（插件：定位 / 正文 / 关系 / 兼容 / 外部源指针 / 出现在哪些包）；分子由 `build.mjs` 算，**不写进 front-matter**。与「资料填充率」的区别：它是**我们自己的字段完备度**，且每个缺项都可点击直达贡献入口。

**② 按钮组（读的位置就是贡献的位置）**

| 按钮 | 行为 |
| --- | --- |
| 编辑此条 | 深链到 GitHub 编辑该文件 |
| 纠错 | Issue 模板，预填词条 id 与当前字段值 |
| **为它写一篇教程** | 领号 → `tutorial/<n>.md` 骨架，**自动写入 `plugins: [{ entry: plugin/12, why: "" }]` 与 `prereq`** |
| **派生概念 / 资料** | 同上，自动带父级引用 |
| 复制安装命令 | `dsh plugin …` |

红链解决「缺条目」，这里解决「已有条目的下级内容」——两者合起来才是完整的生长闭环。

## 5. 包成分表（MC百科合成表的对应物）

MC百科让人上瘾的机制之一是合成表：一眼看懂「这个东西由什么组成」。DSH 的对应物是**整合包配方**——一个 `.dspack` 由哪些层栈、依赖、技能、预设、全局指令构成。

```
┌ 配方：desktop-pack ─────────────────────── 类型 profile ──┐
│                                                            │
│  产物                      配方                            │
│ ┌──────────┐   ┌──────────────────────────────────────┐   │
│ │desktop-  │   │ 层栈 bundles（7）                     │   │
│ │pack      │   │  @deepseek-ai/dsh-base                │   │
│ │ v1.0.0   │   │  @deepseek-ai/dsh-web-app             │   │
│ │ DSH      │   │  dsh-pack-plugin · dsh-context · …    │   │
│ │ 0.2.0-rc.2│  ├──────────────────────────────────────┤   │
│ └──────────┘   │ 依赖 dependencies（4）                │   │
│                │  dsh-pack-plugin@0.5.0                │   │
│  [安装命令]    │  github:…/dafy-whale-theme@99e8c57     │   │
│                ├──────────────────────────────────────┤   │
│                │ 技能 skills        │ 预设 presets     │   │
│                │  （dshhome 形态才有）│  （同上）        │   │
│                ├──────────────────────────────────────┤   │
│                │ 全局指令 instructions                 │   │
│                │  AGENTS.md                            │   │
│                ├──────────────────────────────────────┤   │
│                │ patch 层（12 条 config 覆盖）         │   │
│                │  禁用 1 个内置组件 · 覆盖默认模型      │   │
│                └──────────────────────────────────────┘   │
│                                                            │
│ 每个元素都是词条链接；未收录的显示为红链（可申请收录）。    │
│ 悬停显示该元素在本包中的固定版本（来自 dependencies）。     │
│                                                            │
│ 反向：本配方出现在 1 个整合包中 · 数据快照 2026-10-01       │
└────────────────────────────────────────────────────────────┘
```

`patch` 层不能原样展示：实测一个包的 `patch` 是上千行的 YAML 配置树（`dsh-myskin` 的整套设计令牌都塞在里面）。合成表里只呈现**摘要**——「N 条 config 覆盖 / 禁用了哪些内置组件 / 覆盖了哪些默认设置」，完整 patch 折叠在「原始数据」里给需要的人看。

另一个实测细节：`bundles` 里大量条目是 **npm 包名**（`dsh-smooth-stream`、`dsh-myskin`、`@dsh-packforge/dsh-pack-plugin`）而不是 GitHub 仓库名。因此合成表的每个元素都要先过 `data/sources.yml` 的映射表才能连到词条；映射不到的元素渲染为红链 + 包名（而不是假装成词条）。

还有一个**必须诚实呈现的空格**：`skills` / `presets` / `instructions` 三格只在 `type: dshhome` 的包里存在于清单，而当前市场的包**全是 `profile` 形态**（0 个 dshhome 真实样本）。profile 包里的技能只能扫归档目录才知道。所以首版这三格多数时候显示「本包为 profile 形态：技能/预设需解包读取」+ 已解包出的实际数量，**而不是显示空白**——空白会让人以为这包没有技能（`cad-ppt-skills` 就是 5 个技能但清单里一个也看不到）。

### 5.1 安装可视化（插件侧的「合成表」）

整合包的配方回答「这个包由什么组成」，而装**一个插件**时读者的真实焦虑是另一件事：**装了它，我的机器会发生什么、我失去多少控制权**。这件事是可以结构化的，而不是只能用一段免责声明表达：

```
输入：dsh plugin --profile web add github:owner/repo
├─ 解析出的依赖树（含 peer 依赖与钉死的版本 / commit）
├─ 会写入磁盘的路径（profile 目录、$DSH_HOME 下的落点）
├─ 是否触发构建脚本（allowBuilds；pnpm 的 ERR_PNPM_IGNORED_BUILDS 场景）
├─ 申请到的能力（文件 / 网络 / 凭据 / 桌面操控）
└─ 占用的 slot（UI 插槽）以及是否与其他插件抢同一个 slot
```

数据来源：`dsh plugin` 的 pnpm 输出、`package.json` 的 `dsh.client.inject`、`cordis.patch.yml` 的 `insert[].inject`、以及仓库 README 里的风险提示。

**没有采集到的项要显示「未声明」，而不是默认「安全」**——与「无数据 ≠ 0」是同一条纪律。这一页的价值在于：它是插件站点与目录站**结构上做不到**的事（它们只能放一段免责声明）。

设计取舍：

- **不做工作台 3×3 网格的视觉模仿**。DSH 的「配方」不是二维摆放，而是**分层挂载**（层栈按序 + 坐标钉死版本），照抄格子反而失真。抄的是「一眼看懂组成」这个体验，不是像素。
- 每个元素可点击 → 直接跳到该插件词条；把「这个包为什么装着 12 个插件」变成可探索的图。
- 版本钉死信息直接显示（`dsh-pack-plugin@0.5.0`），这是 DSH 与 Minecraft 的关键差异：**可复现**。这正是值得在百科里强调的信息。

## 6. 版本兼容矩阵

MC百科最有用的表之一是「模组 × MC 版本」。DSH 的对应物更关键，因为 DSH 版本带 `rc` 后缀、插件常因升级而失效（`dsh-loader` 就是为这个问题而生的）。

```
           │ 0.1.0 0.1.5 0.2.0 0.3.0
dsh-loader │  ✔     ✔     ✔     ?
pack-plugin│  ✘     ✔     ✔     ?
wallpaper  │  –     –     ✔     ?
```

- 数据来源：插件词条的 `compat.dsh`（人工核实，或搬运 manifest v5 的 `dshVersions` 枚举）、整合包的 `dshVersion` / `dshVersions`。
- 三态：✔ 实测可用 / ✘ 已知不兼容 / `?` 未核实 / `–` 不适用。**「未核实」必须与「不兼容」视觉上区分**——这与市场的下载量口径是同一条纪律（无数据 ≠ 0）。
- 这一页是第一版就值得做的：它把散落在各仓库 README 里的兼容性声明集中成一张可查的表。

## 7. 导航、页脚与视觉

- **顶部导航**：词条索引 / 配方 / 关系图 / 矩阵 / 教程 / 贡献 + 搜索框（固定在头部）。
- **页脚**：数据快照时间、许可证（代码 CC0 1.0，词条 CC BY-SA 4.0）、生态鸣谢与外链（市场 / 规范 / 工具 / awesome / dshbase / DSH 本体）。
- **视觉系统**：与市场**不同的一套**——现代 Wiki / 索引式（青绿品牌色 + 靛蓝链接、系统字体、1px 边框、高信息密度、表格与信息表为一等公民），完整规范见 [08](08-visual-system.md)。市场那套「纸墨朱砂」是宣传页取向，百科复用会让人分不清「这是介绍页还是查资料的地方」。
- **移动端**：正文优先；信息表在窄屏折到正文上方（读者先看「这是什么」再看介绍）。
- **无障碍**：语义标签、TOC 与搜索键盘可达、对比度达 WCAG AA。

## 8. 交互与状态

| 场景 | 行为 |
| --- | --- |
| 搜索无结果 | 显示「没有匹配词条」+ 「申请收录这条」入口 |
| 词条不存在（`/e/...` 打不开） | 404 页显示红链语义 + 搜索框 + 申请收录入口 |
| 采集数据缺失 | 字段显示「无数据」，**不显示 0**，并标注快照时间 |
| 词条是 `draft` | 顶部挂「草稿：内容待完善」提示条 + 贡献入口 |
| 图片缺失 | 占位图（不破版），并在 `validate.mjs` 里已报错 |
| 超长正文 | 目录吸顶；正文按 `##` 折叠（可选，默认展开） |
