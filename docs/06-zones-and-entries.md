# 06 · 分区层（资源整合）与词条层的关系

## 1. 两层架构

主站是两个功能的合体，页面类型、数据来源、贡献方式都不同：

| | **分区层（资源整合）** | **词条层（解释与教程）** |
| --- | --- | --- |
| 回答 | 「这类东西去哪拿」 | 「这是什么、为什么、怎么用」 |
| 形态 | 分区页 + 卡片列表，**大量外链** | 编号词条页 `/<kind>/<n>.html` |
| 内容量 | 一句介绍 + 结构化卡片 | 正文（教程 / 机制解释 / 聚合页） |
| 数据来源 | **我们自己写**：分区页由 `sections`（二级分区）+ 条目组成，每条都指向一个词条或外链；外部源的数字以「引用 + 快照」的形式出现在二级分区的综述里（例：「插件市场」那一节） | 人工撰写 + 引用外部源（带快照） |
| 是否编号 | **不编号**（不是词条，不进 registry） | 编号，永不复用，删除留墓碑 |
| 贡献方式 | 一行 YAML / 一条 prune 建议 | 领号 → 模板 → PR |

两者的桥梁是**红链**：分区页里某个条目还没有本站词条时，显示为灰色虚线 + 「写这一条」入口，点进去直达领号命令与模板。**分区是入口，词条是内容，红链是生长机制**——这是整个站点唯一需要「运营」的地方，而它是自动的。

```
┌─ 分区层 ──────────────────────────────────────────────┐
│ /plugins    /packs    /launchers   /themes   /skills  │
│   ↑ 卡片：名称 · 一句话 · 来源徽章 · 外部链接          │
│   └─ 有词条 → 蓝链进词条；无词条 → 红链「写这一条」    │
└───────────────────────┬───────────────────────────────┘
                        │ 红链 → 领号 → PR
┌───────────────────────▼───────────────────────────────┐
│ 词条层  /plugin/12.html  /tutorial/6.html  /pack/3.html│
│   用户贡献 · 编号永久 · 互相交叉链接 · 反链与反向索引  │
└───────────────────────────────────────────────────────┘
```

## 2. 分区清单（分层是推导规则，展示顺序是编辑决定）

一级分区不按「用途」划（用途是二级标签的活），而按**读者能替换掉 DSH 的哪一层**划。这个规则的好处是：**它能自己推导出新分区**——只要问「这一层还有别的东西可以被换掉吗」。

| 层 | 分区 | 路径 | 收什么 | 数据源策略 |
| --- | --- | --- | --- | --- |
| **① 交互层**<br>你用什么界面在用 | **界面与客户端** | `/clients` | 官方 Web UI、各类桌面端（官方 / 第三方壳 / 启动器内置）、TUI、无界面 CLI 与 headless 跑法 | `curated-list`：人工清单（官方形态 + 第三方前端；见 §2.4） |
| **② 启动层**<br>怎么装上并起得来 | **启动器** | `/launchers` | `.dspack` 的安装端 | `external-index`：`launchers.json`（5 条 canonical ID） |
| **③ 扩展层**<br>给它加功能 | **插件** | `/plugins` | 宿主侧 / 客户端侧插件、bundle、兼容层 | `external-index`：消费 awesome `catalog.json`（4400 条）筛选与跳转 |
| | **MCP 与工具接入** | `/mcps` | 外部 MCP 服务器与桥接：把外面的工具接成 `mcp__<server>__<tool>` | `curated-list`：只收桥接机制与值得单独讲的接法；找服务器去官方合集（我们不做全量收录） |
| **④ 配置层**<br>改它的行为与语气 | **指令与配方** | `/recipes` | 全局指令模板（`AGENTS.md`）、`cordis.patch.yml` 片段、层栈配方 | `curated-list`：人工清单（**DSH 特有**，别处没有） |
| | **预设与人设** | `/presets` | `agent.cordis.yml` 预设、persona / 角色设定 | `curated-list`：人工清单 |
| | **技能包** | `/skills` | `SKILL.md` 技能与技能合集 | `curated-list`：人工清单（可从整合包归档反查） |
| **⑤ 外观层**<br>换它的样子 | **主题与皮肤** | `/themes` | 主题引擎（皮肤加载器）、配色令牌、壁纸、图标包 | `curated-list`：人工清单 |
| | **素材与本地化** | `/assets` | 图标、字体、翻译包（汉化 / i18n） | `curated-list`：人工清单 |
| **⑥ 分发层**<br>一次装一整套 | **整合包** | `/packs` | `.dspack`（profile / dshhome 两形态） | `external-index`：消费市场 `index.json`（当前 8 条）+ 本站词条 |
| **⑦ 元层**<br>规则与工具 | **规范与协议** | `/specs` | manifest / pack-structure / index / publishing / launcher-registry | `external-index`：读规范仓库的文件清单与版本徽章 |
| | **工具链** | `/toolchain` | 打包 / 安装 / 市场 / 索引 / 调试工具 | `curated-list`：人工清单 |

**生成规则（用来找下一个分区）**：沿这七层逐层问「这一层还能被第三方替换吗」——交互层 → 客户端形态；启动层 → 安装端；扩展层 → 插件；配置层 → 预设 / 技能 / 指令 / 配方 / 权限策略；外观层 → 主题 / 图标 / 壁纸 / 翻译；分发层 → 包 / 单项分发；元层 → 规范 / 工具 / 模板。凡是这几层里能独立被安装或替换的东西，都配得上一级分区。

> 这十二个不是终局，是首版够用的一级切分。新增分区的成本很低（一条 YAML + 一个词条类型），**但不要按「用途」去切一级**——那会与二级标签打架（见 §3）。

> ⚠️ **上表「事实源」那一列是旧口径**（`external-index` / `curated-list`）：它属于「分区优先消费外部源、无源的分区才人工清单」那套模型，**已废弃**（理由见 [07](07-multi-source-zones.md) 顶部）。现在分区页的内容是**我们自己写**的：`kinds`（收哪种词条）+ `sections`（二级分区，含编辑综述）+ 条目。外部源的数字以「引用 + 快照」写进相应二级分区的综述里。

### 2.00 展示顺序：编辑决定，写在 `data/registry.yml` 的 `zoneOrder`

**上表的分层是「怎么推导出分区」，不是「读者先看哪个」。** 展示顺序是编辑决定，
唯一来源是 `data/registry.yml` 的 `zoneOrder`（构建期的 `zones/index.json` 与站点侧栏都按它排）。
在此之前顺序是**按分区 id 字母序**，于是侧栏读起来是「素材与本地化 → 界面与客户端 → 启动器…」——
顺序由字母决定，这是错的。

现在的顺序（先是你每天要用的，**规范垫底**——它是查阅用的，不是入口）：

| # | 分区 | 一句话 |
| --- | --- | --- |
| 1 | 界面与客户端 `clients` | 你从哪用 DSH |
| 2 | 插件 `plugins` | 装什么功能 |
| 3 | 技能包 `skills` | 教它怎么做 |
| 4 | 启动器 `launchers` | 怎么装、怎么起 |
| 5 | 整合包 `packs` | 一次装好一套 |
| 6 | MCP 与工具接入 `mcps` | 把外面的工具接进来 |
| 7 | 主题与皮肤 `themes` | 长什么样 |
| 8 | 素材与本地化 `assets` | 图标 / 字体 / 翻译 |
| 9 | 预设与人设 `presets` | 它是什么性格 |
| 10 | 指令与配方 `recipes` | 一小段就能改行为 |
| 11 | 工具链 `toolchain` | 做包与发布用 |
| 12 | 规范与协议 `specs` | **垫底**：有争议时以它为准 |

前五个是评审点名的顺序（界面与客户端 → 插件 → 技能包 → 启动器 → 整合包），
第六个起是「其余的」——**新增分区默认落在这段里，不要插进前五个之间**。

校验规则 26 保证这份顺序与 `data/zones/*.yml` **完全对应**：漏一个（会被排到最后）、
多一个（顺序表里有幽灵）都算 error。所以「新增分区忘了排顺序」不会静默发生。

### 2.0 每个分区声明自己收哪种词条（`kinds:`）

分区文件里有一个 `kinds:` 键，声明这个分区的条目对应**哪种词条类型**：

```yaml
zone: themes
title: 主题与皮肤
kinds: [theme]        # 这个分区能长出 theme/<n> 详情页
```

**为什么要有它**：早先 kind → 分区是构建期用正则从分区名里猜的，猜错过（`concept` 被算成「规范与协议」），
而且新增分区或新增类型时会静默失效——**一个分区没有对应类型，它的条目就永远只能是外链卡片**。
现在：类型共十五种（十二个分区类型 + `concept` / `tutorial` / `source` 三个跨分区类型），
校验规则 24 要求「一种类型恰好被一个分区声明」，见 [12](12-m2-kinds.md)。

跨分区那三种**不写进任何分区**：概念与教程是「读的东西」，不属于任何一层；
一条**资源源**本身覆盖多个分区（用它的 `zones:` 声明覆盖谁），也不属于某一层。

### 2.0.1 二级分区：一个分区内部再分「是什么东西」

一级分区回答「这是哪一层」，二级分区回答「**同一层里的东西属于哪一类**」。
例子（用户在评审时给的判据）：

- **插件** → `插件市场`（市面上的源与目录，负责发现与全量收录） / `插件`（本站收录的插件聚合页）
- **主题** → `主题包`（换出来的一套东西） / `主题加载器`（把它加载进界面的那个机制或插件）

**为什么需要它**：一级分区里混着两种东西时，读者分不清「我该点哪个」。
插件层尤其明显——「插件市场」是**去源头**的地方，「插件」是**读条目**的地方，
它们的语域不同（前者是编辑综述 + 引用外部数据，后者是词条聚合，见 [11](11-three-registers.md)）。

数据模型（`data/zones/<zone>.yml`）：

```yaml
zone: plugins
title: 插件
kinds: [plugin]              # 本分区条目主要对应哪种词条类型

sections:                    # 二级分区；不写就是不分组的扁平清单（向后兼容）
  - id: markets
    title: 插件市场
    desc: 市面上主流的插件源与目录：它们负责「发现」与全量收录
    intro: |                 # 可选：编辑综述（Markdown），板块页语域——介绍主流玩家并引用他们的数据
      插件生态现在有四家在做不同的事……
  - id: plugins
    title: 插件
    desc: 本站收录的插件聚合页：官方本体 + 被教程引用过、或被整合包用到的第三方插件
    intro: null

items:
  - name: awesome-dsh-plugin.com
    section: markets         # 归到哪个二级分区；zone 里声明了 sections 就必须写
    blurb: …
```

规则：

1. `sections[].id` 在同一分区内唯一；`items[].section` 必须指向本分区声明过的 id（校验规则 25）。
2. 声明了 `sections` 的分区，**每个条目都要有 `section`**（漏了是 warning，不是 error——允许边加边归位）。
3. `intro` 是可选的编辑综述，**按板块页语域写**：介绍这一类的玩家/机制与取舍，并引用外部数据（标快照）。
   它由构建期渲染成 HTML（`introHtml`），前端直接插入。**它不是词条正文**——具体某一条的内容属于词条页。
4. 二级分区**不编号、不进 URL**：它们是分区页内部的锚点（`#sec-<id>`），词条的永久地址仍然是 `/<kind>/<n>.html`。

### 2.1 我另外想到、但建议**先不立区**的候选

| 候选分区 | 为什么不先立 | 更好的去处 |
| --- | --- | --- |
| MCP 服务器与工具桥 | 生态里体量还小，且本质是「插件的一种」 | 插件分区 + 二级标签 `mcp` |
| 模型与账号接入 | 多由内置组件或配置项实现，不是可下载资源 | 概念词条 + 「预设与人设」分区 |
| 会话与记忆后端 | 目前形态是插件 | 插件分区 + 标签 `memory` |
| 权限与沙箱策略 | 是配置而不是分发物 | 「指令与配方」分区 |
| 游戏化玩法 / 桌宠 | 是插件的子集 | 插件分区 + 标签 `fun` |
| 云端 / 远程部署 | 生态尚未成形 | 观察，出现 3 个以上再立区 |
| 项目模板 / 脚手架 | 目前只有打包工具自带模板 | 「工具链」分区 + 标签 `template` |

判断标准：**「它能不能独立被安装 / 运行 / 替换？」** 能，就配得上一个一级分区；不能，就是标签或词条。

### 2.3 「界面与客户端」分区怎么描述（这是最容易与启动器混淆的一个）

**一句话定义（写进 `desc`）**：

> 你从哪、以什么界面使用 DSH：官方 Web UI、各类桌面端、终端界面（TUI）、无界面 CLI 与 headless 跑法。「启动器」管的是装上与起得来，这里管的是用起来是什么样。

| 与它容易混的分区 | 边界规则 |
| --- | --- |
| **启动器**（`/launchers`） | 一个东西若主要是「装包 / 选版本 / 一键启动」，归启动器；若主要是「提供一个界面让人和 DSH 对话」，归这里。**同一个实体可以同时挂两个分区**（`entities.yml` 保证只出现一份数据，卡片各分区各显示一次）——例如官方桌面端既是 `official-desktop` 启动器，也是一种客户端形态 |
| **插件**（`/plugins`） | 插件是**挂在某个界面里的扩展**（改侧边栏、加面板）；客户端是**承载界面的那个东西**。`dsh-wallpaper-engine` 改的是 Web UI 的背景 → 插件；某个第三方重写的 Web 前端 → 客户端 |
| **主题与皮肤**（`/themes`） | 主题改的是**同一个界面里的样子**；客户端换的是**界面本身** |

**该分区的条目不只有卡片通用字段，还要声明形态**（这是它唯一需要的专属字段，机制见 §4 的 `itemFields`）：

```yaml
- name: 官方 Web UI
  blurb: 浏览器里的完整界面，dsh web 启动（等价于 --profile web）。
  form: web                 # web | desktop | tui | headless | cli
  shippedBy: official       # official | third-party | launcher
  platforms: [windows, macos, linux, browser]
  profile: web              # 对应的 profile 名（若能对应）
  links: { github: "deepseek-ai/deepseek-harness" }
- name: 某第三方 TUI 客户端
  blurb: 终端里的原生界面，低带宽环境友好。
  form: tui
  shippedBy: third-party
  platforms: [windows, macos, linux]
  links: { github: "owner/repo" }
```

三个必须写清的字段：

1. **`form`**：`web` / `desktop` / `tui` / `headless` / `cli`——读者最关心的就是这一条（我先要图形界面还是终端）。
2. **`shippedBy`**：`official` / `third-party` / `launcher`——**官方与第三方必须可区分**，这是信任前提（尤其第三方桌面壳会拿到本机权限）。
3. **`profile`**：能对应到 `--profile <name>` 的写出来（`web` / `headless` 是 DSH 自带模板，第三方形态通常有自己的 profile）。这直接把分区页和「怎么启动」连起来。

> 首版内容：官方 Web UI、官方桌面端、`dsh-cli`（无启动器直用命令行）、`headless` 跑法 4 条官方形态；第三方桌面端与 TUI 各留 1–2 条占位，标「欢迎补充」。**宁可先空着，也不要拿插件冒充客户端。**

### 2.2 一个分区里有多个源怎么办

这不是例外，而是常态：插件分区已知就有四个源（`awesome-dsh-plugin.com` / `dshbase.com` / npm / GitHub topic），启动器分区除了注册表里的 5 条还有个人自研的。处理方式是三条机制——**源可插拔**（新增源 = 加一条 `adapter` 配置）、**实体归并**（多源同物靠 `repo:` / `npm:` 键合成一张卡）、**三级呈现 + 全量外链**（有词条 > 有生态证据 > 只在源头）。

于是分区页顶部会多出一个**「本分区的来源」区块**，列出覆盖该分区的所有源及其状态；卡片则是多源合并的结果，字段冲突照实并列。完整设计见 [07](07-multi-source-zones.md)。

## 3. 二级筛选：复用外部源的用途标签，不另造

一级回答「装什么」，二级回答「干什么」。**二级标签直接对齐 `awesome-dsh-plugin.com` 的 24 个分类键**（`UI 增强` / `记忆` / `会话与消息` / `工具与能力` / `安全与权限` / `开发与运行时` / `视觉与多模态` / `语音与音频` / `浏览器与网页` / `远程与移动端` / `通知与集成` / `工作流与自动化` / `Git 与代码评审` / `主题与外观` / `用量与计费` / `模型与账号接入` / `文档与渲染` / `技能包` / `插件市场与管理` / `娱乐` / `AGI 架构探索` / `身份与通信` / `WSL 与 Windows 互操作` / `工具与能力`）。

理由：同一个插件在 awesome 与本站落在不同的类里，读者和下游机器都要多做一次映射。只有当某个分区确实需要更细的划分时（例如「主题与皮肤」需要区分主题引擎 / 配色 / 壁纸 / 图标包），才补本站的第二层标签。

```
┌ /themes · 主题与皮肤 ─────────────────────────────────────┐
│ 换掉 DSH 的样子：主题引擎、配色令牌、壁纸与图标包。        │
│ 怎么用：装法与落点随类型不同，见每个条目的说明。           │
│ 数据来源：本站人工清单（2 项来自整合包解包） · 快照 10-02  │
├───────────────────────────────────────────────────────────┤
│ [ 搜索 ]  [ 全部 · 主题引擎 · 配色 · 壁纸 · 图标包 ]       │
│                                                           │
│ ┌ dsh-myskin ─────────────────────────────┐ ┌ Wallpaper…┐│
│ │ 主题引擎：改整套设计令牌        词条 →  │ │ 把本机…   ││
│ │ 装：dsh plugin add …           插件/12  │ │ 词条 红链 ││
│ │ 标签：主题与外观 · UI 增强              │ │ 写这一条 →││
│ │ 外部：npm ↗ · GitHub ↗ · awesome ↗      │ │           ││
│ └─────────────────────────────────────────┘ └───────────┘│
└───────────────────────────────────────────────────────────┘
```

卡片统一字段（**这是分区层的全部数据契约**，越薄越好）：

| 字段 | 必需 | 说明 |
| --- | --- | --- |
| `name` | ✅ | 名称 |
| `blurb` | ✅ | 一句话介绍（**人工写**，不抄上游 description） |
| `source` | ✅ | 来源徽章：`awesome` / `market` / `launchers` / `curated` |
| `links` | ✅ | 外部链接（npm / GitHub / 详情页 / 发布页），至少一个 |
| `entry` | 否 | 本站词条 id（有则显示蓝链，无则显示红链「写这一条」） |
| `completeness` | 否 | **构建期派生**：该词条的字段完备度小标（如 `78%`），让分区页也能看出「哪条还没写全」——把编辑驱动力放回分区层 |
| `tags` | 否 | 二级用途标签（§3） |
| `version` / `updatedAt` | 否 | 来自外部源，带快照时间 |
| `risk` | 否 | 风险徽章：`desktop-control` / `network` / `credentials` / `build-script`（见 §7 想法 1） |

### 4.1 分区专属字段（`itemFields`）：通用卡片 + 少量专属

卡片字段刻意做得极薄（上面七项），但个别分区确实需要自己的字段——**「界面与客户端」需要 `form` / `shippedBy` / `profile`**（§2.3），「启动器」需要 `lineage`（[07](07-multi-source-zones.md) §6）。

做法：分区文件声明自己的**专属字段白名单**，条目里只允许出现白名单内的额外键。这样既不用为每个分区写一套 schema，也不会让条目变成随手塞字段的垃圾袋：

```yaml
zone: clients
title: 界面与客户端
itemFields: [form, shippedBy, profile, platforms]   # 白名单，通用字段之外只允许这些
items:
  - name: 官方 Web UI
    form: web
    shippedBy: official
```

两条硬规矩：

1. 条目出现白名单之外的键 → error（宁可拒绝，也不让分区页慢慢长歪）。
2. **通用卡片键不能写进 `itemFields`**（`name` / `blurb` / `source` / `links` / `entry` / `completeness` / `tags` / `version` / `updatedAt` / `risk`）。构建会把 `itemFields` 里的键塞进 `item.extra`，于是顶层字段消失——**我们踩过一次**：11 个分区都把 `source` 声明进了 `itemFields`，结果来源徽章全部渲染不出来。校验器现在对这条报 error。

## 5. 两类数据源策略与刷新纪律

| 策略 | 适用分区 | 数据怎么来 | 纪律 |
| --- | --- | --- | --- |
| `external-index` | 插件、整合包、启动器、规范 | 消费外部源的 JSON（awesome `catalog.json` / 市场 `index.json` / `launchers.json`） | 只做筛选与跳转，**不落元数据副本**；页面标快照时间；外部源挂了沿用上轮快照 |
| `curated-list` | 技能、预设、主题、指令与配方、工具链、素材 | 人工 YAML（`data/zones/<zone>.yml`） | 每条只需 `name` / `blurb` / `links`；**宁缺毋滥**，一条冗余条目比没有更糟 |

分区层**不追求完整**：它的目标是「读者能找到入口」，不是「穷举生态」。任何试图在分区层做全量的冲动，都应该转成「去 awesome / dshbase」的外链。

## 6. 分区层与词条层的连接

1. **红链 → 领号**：分区页看到没有词条的条目，入口直接给 `node scripts/new.mjs plugin "<名称>"`（或 issue 模板）。这是词条增长的主要来源。
2. **词条反向显示所在分区**：词条页顶部显示「属于：插件分区 · 标签：UI 增强」，点击回到分区页对应筛选。
3. **分区页的排序不用评分**，用两个客观量：**被本站教程引用次数**与**被整合包使用次数**（都来自构建期反向索引）——没有后端也能算，且不可刷。
4. **同一实体只在一个分区出现**（插件就是插件），跨分区的关系用「相关」链接表达（例如某整合包与它使用的主题互相链接）。

## 7. 我另外提的五个想法（超出当前需求的，供取舍）

1. **风险徽章**。awesome 只能用一段免责声明提醒「装插件等于跑第三方代码」；我们可以在插件卡片与词条上打结构化徽章：`桌面操控` / `网络访问` / `凭据` / `构建脚本`（后两个可从 `cordis.patch.yml` 的 `inject` 与 `package.json` 的构建脚本半自动推断）。**这是外部源结构上给不出的信息**，也是 DSH 用户最真实的焦虑。
2. **兼容性筛选进分区页**。分区页加一个「我的 DSH 版本」下拉（默认读取最新），把已知不兼容的卡片灰掉并说明原因。数据来自词条的 `compat`——**只有做了词条层才可能有这个功能**，这是两层架构的复利。
3. **「指令与配方」分区是 DSH 独有的机会**。MC百科的合成表对应物在这里：`cordis.patch.yml` 片段（禁用某内置组件、改默认模型、换配色令牌）、`AGENTS.md` 指令模板、层栈配方。它们体量小、可复制粘贴、极高频，而且**没有任何外部源在收录**。
4. **「装在哪」的落点图**。DSH 的资源落点分散（profile 目录、`$DSH_HOME`、`$DSH_AGENTS_HOME`、项目 `.dsh/`），这是新手最常错的地方。分区页顶部放一张统一的「装什么 → 落在哪 → 怎么生效」小图，比每个条目的 README 讲一遍有效得多。
5. **失效巡检**。外部源条目会归档、改名、下架。`linkcheck.mjs` 定时跑 HEAD 检查，把结果写进 `collected/links.json`，分区页对失效链接标「链接待核」并给搜索回退——**我们比源头更早发现它烂了**，这本身就是价值。
