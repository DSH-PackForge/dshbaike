# 07 · 多源分区：一个分区里有好几个做同一件事的源

> 状态：**设计稿（待评审）**。本文解决一个结构性问题：插件分区里不止 awesome 一家在做插件收录，启动器分区里也不止一个人在写启动器。**一个分区 = 多个源 + 一个实体归并层**，而不是「一个源的一张表」。
>
> 关联：[06](06-zones-and-entries.md)（分区层与词条层）、[02](02-data-contract.md)（字段契约）、[03](03-directory-and-pipeline.md)（工程落地）。

---

## 1. 问题：源是复数，而且会长出来

| 分区 | 已知或可预期的源 |
| --- | --- |
| 插件 | `awesome-dsh-plugin.com`（4400 条）、`dshbase.com`（7800+ 条）、npm registry、GitHub topic `dsh-plugin`、未来还会有别人的清单站 |
| 整合包 | `dsh-pack-market`（8 条）、`dshbase.com` 的场景包、将来其它启动器自建的市场 |
| 启动器 | 规范里的 canonical ID 认领表（5 条）+ **个人自研/魔改的启动器**（DSHL 是 PCL2 魔改、HDSL 是 HMCL 内核，名字只差一个字母） |
| 主题 / 技能 / 预设 / 配方 | 目前没有成规模的源，但**迟早会有**（至少会有别人的清单、gist、合集仓库） |

如果按「一个分区一张表」去设计，结果是：每出现一个新源，就要么把它整表镜像进来（法律与维护成本），要么手工合并（永远做不完）。所以必须换一个模型。

---

## 2. 三条机制

| 机制 | 回答什么 | 落地 |
| --- | --- | --- |
| **① 源可插拔** | 「又出现一个插件源怎么办」 | 新增一个源 = **加一条配置**，不改代码：源声明自己的入口、字段映射、刷新频率、许可、可信度 |
| **② 实体归并** | 「同一个插件在两个源里都有，会不会出现两遍」 | 多源条目归到**一个实体**（键匹配：`owner/repo` → npm 包名），一张卡片 + 多个源链接 |
| **③ 三级呈现 + 全量外链** | 「我们不收录的那几万条怎么办」 | 分区页分三档：**有词条 > 有生态证据 > 只在源头**；最后一档只给外链入口，**不落库** |

外加两条纪律：

- **④ 认领与自治**：启动器的 canonical ID、源的「本站收录申请」都走规范仓库 PR，我们只做索引与提醒（§6）。
- **⑤ 巡检与状态**：源会改名、归档、烂掉。每个源与每条外链都有状态，页面如实标注（见 [06](06-zones-and-entries.md) §7 想法 5）。

## 3. 源适配器契约

**源有两半，职责不同**：

| 半 | 位置 | 读者 | 谁评审 |
| --- | --- | --- | --- |
| 解释（它是什么、字段有哪些、怎么投稿、与我们的关系） | `data/source/<n>.md`（编号词条） | 人 | 内容评审 |
| 抓取配置（adapter） | 同一词条的 front-matter 的 `adapter` 子对象 | `collect.mjs` | 同一次 PR |

> 还没写词条、但已经在消费的源，允许存在 `data/sources/<slug>.yml`（纯配置，页面标「未文档化」）。它与同 slug 的源词条**不能并存**，校验器报错。

```yaml
adapter:
  zone: [plugins]                    # 覆盖哪些分区（可多个）
  endpoint: https://awesome-dsh-plugin.com/zh/catalog.json
  format: json                       # json | api | html
  auth: none                         # none | token（token 名前缀，不进仓库）
  fields:                            # 源字段 → 我们的卡片字段
    name: name
    owner: owner
    cat: category
    stars: stars
    dl: downloads30d
    npm: npmInstallable
    cmd: installCommand
    added: addedAt
    href: detailUrl
  license: 见 04 §7.3（站点自述 MIT，市场页脚写 CC0，口径冲突已记录）
  cadence: daily                     # daily | weekly | manual
  reliability: high                  # high | medium | low：失败时是否允许降级沿用上轮
  status: active                     # active | stale | dead —— 由巡检写入，不由人手改
```

规则：

1. **字段映射是显式的**：源的字段名与我们的卡片字段名不同，必须逐个映射；映射不到的源字段不猜。
2. **`reliability` 决定降级行为**：`high` 的源失败时沿用上轮快照并**不报警**；`low` 的源失败只记录、不参与构建（避免一个野源拖垮全站）。
3. **同一个源可以覆盖多个分区**（`zone: [plugins, skills]`），分区页从所有覆盖该分区的源聚合来源区块——**这是「新增源自动出现在分区里」的关键**。
4. **配额与礼貌**：抓取频率写入配置，每轮的请求预算先算后抓（同 [03](03-directory-and-pipeline.md) §6.3）。

## 4. 实体归并契约（`data/entities.yml`）

同一个东西在多个源里出现时，必须归到一张卡上，否则分区页会出现三遍 `dsh-loader`。

```yaml
version: 1
entities:
  - id: plugin/12                        # 已建词条则指向词条；未建则用 external:<slug>
    keys:                                # 归并键：精确匹配，不做模糊
      - repo:DSH-PackForge/dsh-pack-plugin
      - npm:@dsh-packforge/dsh-pack-plugin
    refs:                                # 采集生成，人工不手改
      - source: awesome
        url: https://awesome-dsh-plugin.com/zh/p/DSH-PackForge/dsh-pack-plugin/
        at: 2026-10-01
        fields: { stars: 5159, downloads30d: 464583, addedAt: 2026-08-14 }
      - source: npm
        url: https://www.npmjs.com/package/@dsh-packforge/dsh-pack-plugin
        at: 2026-10-01
        fields: { latest: 0.3.5 }
```

规则：

1. **自动归并只在归并键精确匹配时发生**（`repo:` 与 `npm:`）。**名字相似一律不自动合并**——错并把两个不同的插件合成一页，比漏并（并排出现两次）对信任的伤害大得多。
2. **一个键只能属于一个实体**（冲突即 error）。人工要合并两个实体时，改 `keys` 并提交，由评审确认。
3. `refs` 由 `collect.mjs` 生成、入库、带快照时间；**人工只维护 `id` 与 `keys`**。
4. 卡片上的**字段冲突照实并列**，不取平均、不挑一个：`star 5159（awesome）· 最近版本 0.3.5（npm）`。多源的价值就在于「同一实体在不同源里的差异是可见的」。

## 5. 分区页因此长这样

以 `/plugins` 为例（`/packs`、`/launchers` 同构）：

```
┌ /plugins · 插件 ─────────────────────────────────────────────┐
│ 给 DSH 加功能：宿主侧/客户端侧插件、bundle、兼容层。          │
│ 怎么装：dsh plugin --profile <name> add <npm 包名 | github:…> │
│ 「装在哪」：profile 目录（见落点图）                          │
├── 本分区的来源（4）──────────────────────────────────────────┤
│ awesome-dsh-plugin  4400 条 · star/下载量 · 每日   ↗ 去发现   │
│ dshbase             7800+ 条 · 中文分类 · 每日     ↗ 去浏览   │
│ npm registry        包名与版本权威                 ↗ 去搜索   │
│ GitHub topic        社区自打标签（≥6000，未核实）  ↗ 去逛     │
├── 本站已收录（12）──────────────────────────────────────────┤
│ [卡片] 多源合并 + 词条链接 + 标签 + 风险徽章 + 出现在哪些包   │
├── 有生态证据但未收录（26）──────────────────────────────────┤
│ 按「被几个整合包使用」排序 · 每条带「写这一条 →」红链         │
├── 只在源头（全量）──────────────────────────────────────────┤
│ 我们不镜像全量：给上面四个源的入口 + 关键词跳转回退           │
└──────────────────────────────────────────────────────────────┘
```

**「本分区的来源」区块不是装饰**：它同时起三个作用——告诉读者「我们不是唯一入口」、给外部源导流（它们也会链回我们）、以及**当某个源烂掉时能就地标注状态**。

## 6. 启动器分区的特殊处理

启动器与插件不同：**它不是「收录问题」，而是「身份认领问题」**。很多人各写各的启动器，需要一个 canonical ID 才能被整合包声明支持（`manifest.launchers`）。

| 段 | 内容 | 机制 |
| --- | --- | --- |
| **已认领**（5 条） | `dshl` / `hdsl` / `dsh-packforge-app` / `official-desktop` / `dsh-cli` | 每条一个词条；事实源是 `launcher-registry.md` + `launchers.json` |
| **未认领 / 个人自研** | 有仓库、有 README，但没在注册表里认领 ID 的启动器 | **允许收录**，但卡片显式标「未在注册表认领」+ 认领引导（向规范仓库提 PR） |
| **血缘与谱系** | 补一个外部源给不出的字段：`lineage`（PCL2 魔改 / HMCL 内核 / 官方 / 自研）、`platforms`、`selfVersioning`（版本自报格式，如四段式 `0.1.1.2`）、`importSupport`（是否支持 `.dspack` 导入） | 人工填写，评审确认 |

为什么值得这么做：**`dshl` 与 `hdsl` 只差一个字母却毫无关系**（一个 PCL 系、一个 HMCL 系）。分区页把血缘摆在卡片上，是任何外部清单都做不到的事。

## 7. 通用答案：任何「很多人在做同一件事」的分区都照这套办

以后主题、技能包、预设、配方分区长出多个源时，处理方式完全一样，不需要新设计：

1. **先加源，再加条目**——源进 `adapter`，条目自动出现在对应分区；
2. **实体归并靠键，不靠名字**——`repo:` / `npm:` / 未来的 `preset:` `skill:` 前缀；
3. **三档呈现**——有词条 / 有生态证据 / 只在源头；
4. **认领是生态自治**——canonical ID、源申请都提 PR，我们只做索引；
5. **状态可见**——源与链接都有 `status`，烂掉就说烂掉。

反过来，如果某个分区**只有一个源**（例如整合包目前只有市场），也照这套写：源的区块里就一项，页面结构不变——**这样新源出现时不用改模板**。

## 8. 反模式（明确不做）

| 反模式 | 为什么不做 |
| --- | --- |
| 把某个源整表镜像进来 | 法律风险（上游许可各异）+ 维护成本随生态线性增长，且永远比源头旧 |
| 做「源之间的排行榜」 | 那是运营与站际比较，不是百科该干的事；还会把新源挡在门外 |
| 用名字模糊匹配自动合并实体 | 错并（把两个插件合成一页）比漏并（并排两次）伤害大得多 |
| 要求一个分区只有一个权威源 | 等于逼我们自己做全量收录，正是这次要避开的 |
| 手工合并多源条目 | 源会变、条目会增，手工合并永远做不完；必须落在 `keys` 上并让采集自动归并 |
