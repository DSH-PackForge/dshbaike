## 一句话

DSH 的插件不是「第三方生态」才有的东西：**本体就是一堆插件**，全部住在这个仓库的 `packages/` 下。
你装的每个 profile，都是从这里挑一批包叠起来跑的。

## 它解决什么问题

新手最容易问错的问题是「有没有插件能让我做 X」——因为 DSH 里 X 很可能**本来就有**，
只是它以一个 `@deepseek-ai/*` 包的形式存在，而不是一个能搜到的第三方插件。
这一条的作用是给插件区打地基：先认清官方提供了什么，再去第三方里找补的那部分。

## 里面有什么

`packages/` 下有 **61 个一级分组**（快照 2026-10-02），大致可以这么读：

| 分组（举例） | 是什么 | 对应哪一半 |
| --- | --- | --- |
| `core` / `boot` / `runtime-diagnostics` | 启动、装配、profile 与 patch 层序 | 宿主 |
| `tool-*`（本机实装 21 个） | 模型能调用的工具：bash / pwsh / fs / web / todo / subagent… | 宿主 |
| `client-ui-*`（本机实装 43 个） | 界面的每一块：聊天、会话列表、设置、侧栏、计划、任务… | 客户端 |
| `session*` / `compaction` / `storage` | 会话持久化、压缩、查询 | 宿主 |
| `sandbox` / `guard` / `credentials` | 沙箱、授权、凭据 | 宿主 |
| `skill` / `preset` / `plan` / `goal` | 能力与工作方式：技能、预设、计划、目标 | 两侧 |
| `mcp` | 把外部 MCP 服务器的工具接进来（见 [[mcp/1]]） | 宿主 |
| `web` / `deliverables` / `document` | 浏览器界面、交付物、文档能力 | 两侧 |

也就是说：**你在界面上看到的每一块、模型能调的每一个工具，都是这里的一个包**。

## 怎么用它

- 官方包**跟着 profile 的组合包一起来**，一般不用手动装；
- 往某个 profile 加第三方插件：`dsh plugin --profile <name> add <包名>`（README 用法表的原话是
  「通过在 profile 目录中转发给 pnpm 来管理该 profile 的插件」）；
- profile 的 `package.json` 里有 `dsh.profile.bundles` 列表，组合包**先从 dsh 安装目录解析**
  （`@deepseek-ai/dsh-base`、`@deepseek-ai/dsh-web-app`…），找不到才去外面拿。

## 为什么值得单列一条

三个理由，都是实操层面的：

1. **避免重复造轮子**——想写「让模型能读 PDF」之前，先看 `document` / `deliverables` 里有没有；
2. **分清两半端**——`client-ui-*` 那些包是客户端半端的既有实现，第三方插件要挂界面就得和它们打交道；
3. **它是「官方口径」的来源**——本站在别处引用 DSH 的行为时，依据写的就是这个仓库的源码与 README，
   而不是二手转述。

## 怎么自己核实

本机就能核，不用联网：

```text
~/.dsh/profiles/node_modules/@deepseek-ai/        # 实装了多少包，目录数就是答案
~/.dsh/profiles/node_modules/@deepseek-ai/dsh/README.zh.md
```

数字与结论都是 **2026-10-02** 的快照：star / fork / 许可取自 GitHub API，
包数与分组取自本机 profile 与仓库目录列表。这类数字会变，引用时请标快照日期。

## 与插件区其他条目的关系

本站插件区里**还有词条**的第三方插件是 [[plugin/2]] dsh-pack-plugin（整合包管理）。

另外两样东西**不属于这一区**，所以没有插件词条：`dsh-loader`（升级兼容层，第三方）在教程 [[tutorial/1]] 里讲；
`dsh-packforge-app`（GUI + dspack CLI）不是插件，它在本体工具链那侧——见 [[tool/1]] 与工具链分区。
这一条不替它们说话，只负责说清地基在哪里。
