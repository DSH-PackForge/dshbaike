## 一句话

DSHL 是 **Windows 上「装上并起得来」那一步的承载者**：它不是一个 DSH 插件，而是 DSH 外面的启动器（照上游说法是 Plain Craft Launcher 的二次开发）。在 `.dspack` 生态里它的身份是 **canonical ID `dshl`**——这个 ID 才是整合包能声明「我支持谁」的凭据。

## 身份：为什么 ID 比仓库名重要

整合包的 manifest v5 有一个可选的 `launchers` 字段（§13），**键就是启动器 ID**：简式是 ID 列表（`["dshl","hdsl"]`），全式是 ID → 支持声明（`{"dshl": "0.2.0", "official-desktop": false, "dsh-cli": {"supported": false, "reason": "…"}}`）。所以「某个包支不支持 DSHL」在规范里是**可判定的事实**，而不是读 README 得出的印象。

本机市场索引里**实测只有 2 个包写了 `launchers`**（快照 2026-09-30，8 个包中）：

| 包 | manifest | `launchers` 实测值 |
| --- | --- | --- |
| `hxh230802.smoother-deepseek-harness` | v5 | `{ "dshl": true, "hdsl": true, "dsh-packforge-app": true, "official-desktop": true }`（全式，四个 ID 全 true） |
| `yukitakasama.better-deepseek-harness-codex` | v5 | `["dshl", "dsh-packforge-app"]`（简式） |

**这张表说明的是生态现状**：`dshl` 两次都被写上，是最常被声明的启动器之一；但**其余 6 个包一个都没写**——不写等于「通用包」，任何启动器都按现状装。所以「包没写 `launchers`」**不是**「不支持 DSHL」。

## 版本自报与判定规则

DSHL 是**唯一一个把自报格式写进规范表的**条目：注册表名称 `PCL-Deepseek-Harness-Launcher（PCL2 魔改）`，ID `dshl`，版本自报 ✅ **四段式（如 `0.1.1.2`）**（`specs/launcher-registry.md` §1）。

判定规则（`launcher-registry.md` §3 + `pack-structure/v3.md` §9.1）：

1. **比较方式**：按 `.` 分段、**逐段数值比较**、**缺段视为 0**（`1.2` ≡ `1.2.0`）；
2. **不做预发布语义**：`rc` / `beta` 在启动器版本上不被解释（那种形态只出现在 DSH 版本里）；
3. **只提示、不硬拒**：不满足 `minVersion` 轻提示后**放行**；`supported:false` 是重警告、**也放行**；放行必须在安装日志留痕；
4. **自报不出来 = 版本未知**：`minVersion` 一律按「版本未知」处理，轻提示后放行。

**这四条合起来是一句设计声明：启动器兼容声明不是门禁。** 你也可以用 DSHL 装一个「声明要更高版本 DSHL」的包，只是会看到提示——但这意味着**警告要真读**，它是唯一的反馈渠道。

## 与它的同音邻居：hdsl

规范表专门写了防混淆警告：`dshl`（PCL 系）与 `hdsl`（Hello 系）**一个字母之差、完全无关**。这不是洁癖——两个 ID 在 issue、README、`launchers` 字段里互相写错，后果是「声明支持的启动器其实没被声明」。写包时请从注册表复制 ID，不要手打。

- **`importSupport`（是否支持 `.dspack`）**：**支持**——编辑确认（2026-10-02）。此前分区文件里这一项是 `importSupport: null`（未声明），
  现在卡片上的口径是 `支持 .dspack（编辑确认 2026-10-02，未逐仓库实测）`。这就是本词条原来把它列进「未核实」的原因——现在有结论了。
