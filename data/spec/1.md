## 一句话

manifest v5 是 **`.dspack` 的清单头契约**，也是本站「一切字段争议的最终裁判」：有争议时以规范仓库的文件为准，而不是以某个包的现状或某个启动器的实现为准。

一句话概括 v5 相对 v4 的变化：**v4 只会描述「一个 profile」，v5 用 `type` 同时描述「一个 profile」和「一整个 `$DSH_HOME`」。**

## 两种形态

| | `type: "profile"` | `type: "dshhome"` |
| --- | --- | --- |
| 是什么 | 单 profile 的层栈（即 v4 契约） | **整个 `$DSH_HOME` 快照** |
| 必需字段 | `bundles`、`dependencies` | `defaultProfile`、`profiles` |
| 可选字段 | `profileName`、`patch`、`files` | `presets`、`skills`、`instructions`、`files` |
| 承载容器 | `.dspack` v3（`overrides/` → profile 根，可选 `home/` → home 根） | `.dspack` v3（`overrides/` → `$DSH_HOME` 根） |

`"collection"` **仍然预留、校验器直接拒绝**——所以看到 `type: "collection"` 的包，它不是新形态，是无效包。

**dshhome 的范围是硬约束**：它明确**排除 `~/.agents`**（那是另一个共享 agent 配置根），也**排除项目级内容**（项目根下的 `.dsh/`、`.agents/`、`AGENTS.md` / `CLAUDE.md` 跟随 cwd，不随包分发）。

还有一条容易踩的：`profiles` **只含用户自定义 profile**，**不得含 `web` / `headless`**——这两个是 DSH 安装自带的模板（`PROFILE_TEMPLATES`），由 `dshVersion` 决定、不进包。校验器会拒。

## r2 追加的两个可选字段

这两个是「市场现状」与「规范」之间最值得本站讲清的部分，早期包几乎都没写。

### `dshVersions`（§12）：枚举，不是 range

- 它是作者**实测过**的兼容版本**枚举集**（`string[]`）。
- **为什么不是 semver range**（规范原文口径）：range 会诱导声明**未实测的未来版本**，而且 DSH 版本带 `rc` 后缀、range 比较易错。
- 安装决策是**确定性的、永有唯一答案**：`dshVersions ∩ 本机已装` 非空 → 命中多个时**优先 `dshVersion` 指定者、其次集合内最新**；交集为空 → 按 `dshVersion` 提示安装；两者全缺省 → 本机最新已装。
- 老消费者只读 `dshVersion`，**行为不变**（集合被忽略 = 现状）。

**本机市场里的正面样本**：`yukitakasama.better-deepseek-harness-codex` 实测写了 `"dshVersion": "0.2.0-rc.2"` 与 `"dshVersions": ["0.2.0-rc.2", "0.2.0-rc.1"]`（快照 2026-09-30）。两项都在、且 `dshVersion ∈ dshVersions`——这正是规范要求的形态。

### `launchers`（§13）：提示机制，不是门禁

简式与全式**语义等价**（归一化后只剩全式）：列表 → 全 `supported:true`；`"<id>": true` → `{supported:true}`；`"<id>": "<ver>"` → `{supported:true, minVersion:"<ver>"}`；`"<id>": false` → `{supported:false}`；`"<id>": { … }` 原样。

全式**锁定三个字段、不得再增**：`supported`（唯一权威判定位）、`minVersion`（语义是「≥」，**不精确钉死**——启动器会自动更新）、`reason`（警告文案，`supported:false` 时强烈建议）。

**未列出的 ID = 未声明（第三态）**，不等于「不支持」。判定表在 `pack-structure/v3.md` §9.1，核心是**警告放行、不硬拒**，且放行必须在安装日志留痕；启动器版本比较是**逐段数值、缺段视为 0、不做 `rc` 预发布语义**。这条链的其中一端见 [[launcher/2]]。

**本机市场的现状**（快照 2026-09-30，8 个包里只有 2 个写了 `launchers`）：`hxh230802.smoother-deepseek-harness` 用全式（四个 ID 全 `true`），`yukitakasama.better-deepseek-harness-codex` 用简式 `["dshl","dsh-packforge-app"]`。**其余 6 个（含唯一的 v4 包）一个都没写**——所以「没写」是常态，不是不支持。

## 导入时按什么顺序决策

两形态共有的前置是两步：**启动器判定**（警告放行）与 **DSH 版本决策**（`dshVersions ∩ 本机已装`，命中多个优先 `dshVersion`、其次集合内最新）。之后 profile 形态走「建实例 → `overrides/` 落 profile 根 → `pnpm install` → `reconcileProfile` → 可选 `home/` 落 `$DSH_HOME` 根」；dshhome 形态要先确保 `dshVersion` 的 DSH 已安装（未装直接报错），再**逐 profile** 各自安装，最后设 `defaultProfile`。`files[]` / `skills[]` 下载校验失败会**整体回滚**。

## 读旧包的正确姿势

| 你看到的 | 该怎么办 |
| --- | --- |
| `manifestVersion: 4` 的包 | 按 **v4** 的规则读它，**别拿 v5 判它**。v4 没有 `launchers` 字段，也没有 dshhome 形态 |
| `manifestVersion: 5` 但没有 `dshVersions` | 正常。缺省视同 `[dshVersion]`，老消费者本来就只读这个 |
| `type: "collection"` | 无效包，校验器拒绝 |

**「按声明的版本读」不是洁癖**：本机市场 8 个包里 `hxh230802.better-sidebar` 实测就是 `manifestVersion: 4`（快照 2026-09-30），它的 manifest 里连 `launchers` 字段都不存在——这不是它「拒绝了所有启动器」，而是**那个版本根本没有这个字段**。

## 未核实 / 未声明

- **`supersedes: 4` 的措辞**：规范正文用的是「v4 是历史」「v5 的 `profile` 形态即 v4 单 profile 契约」，**并没有出现「v5 取代 v4」的字样**。所以这条属性是**本站的读法**（v5 是 v4 的演进/超集），不是规范的原文声明。
- **历史版本的 `specStatus`**：本站 `data/zones/specs.yml` 里 v1–v4、pack-structure v1–v2 标的是 `specStatus: historical`，而**契约允许的枚举是 `current` / `draft` / `deprecated`**——`historical` 不在其中。本词条只写 `current`，不替历史条目解释。
- **`repo` / 许可证**：`repo` 取自分区文件的规范仓库 URL。**规范仓库根的 LICENSE 本轮未读取**，未核实。
- **规范文件的本地副本口径已变**：词条 [[source/2]] 里写着「本机 checkout 的 `specs/` 下只有 `workspace-config/v1.md` 一个文件」——**本轮实测该口径已不成立**：`DSH-PackForge` 检出下 `specs/` 有 manifest v1–v5、pack-structure v1–v3、index/index.md、publishing/v1.md、launcher-registry.md、workspace-config/v1.md，共 11 份（实测 2026-10-02）。本词条的依据是本机读到的副本。**那两条旧词条是否该更新不在本次任务范围内**（它们是别人的文件）。
- **市场索引的副本完整性**：市场 `index/packs/*/manifest.json` 是**压缩成单行的副本**，字段顺序与上游原包不保证一致；本站引用的是索引副本，**没有下载 `.dspack` 归档比对**。
